## 測定系を先に疑う

このプロジェクトで何度も同じ形で止まった。**「効かない」「壊れている」という観測は、
測定系の欠陥でも全く同じ形で出る。** 実測値を根拠に議論する設計なので、道具が間違って
いると全部が狂う。

実際に踏んだもの:

| 落とし穴 | 症状 | 正しい理解 |
|---|---|---|
| LINEパケットの `ts` の定義 | 隣接行の差が htotal にならず「同期が動いている」と誤読 | `ts` は**ライン先頭 + offset_px**(断片ごとに正しいサンプル時刻を持たせるため)。比べるなら offset を引く |
| entry 変換の式 | 全行が不一致に見えた | `offset_px`/`count_px`[画素] → entry(2画素)は、末尾が `(offset + count - 1)//2` |
| SIMの `hs_offset` | 全画素が1ずれ、不具合と誤認 | RGBは1段・HSOUT/VSOUTは2段のレジスタで受けるので、駆動側が置いた画素と取り込みの x に固定のずれがある。SIMでは `hs_offset=1` で打ち消す |
| A/B比較の交絡 | 「範囲が FIFO段数ぶん遅れる」という誤った結論 | 全ライン送信モード(key 0x30)は送出負荷が60倍違い、FIFOの滞留状態が変わる。**同条件を2回取った自己一致率**を先に出して、ばらつきの下限を示すこと |
| `cap_drops` の読み方 | 42289という値を見て「FIFOが溢れている」と誤読 | 購読していない間は誰もFIFOを抜かないので当然溢れる(92.4%)。**動作中は0**。読むなら購読しながら時間差で2回 |
| 手書きのテストパケット | 「Windowsのパケットが届いていない」と誤読 | 自作の SUBSCRIBE が22バイトだった(本物は16)。ボードは長さを見るので無視される。**プロトコルは実装(`proto.pack_*`)を使う** |
| 自分のブロードキャストの回り込み | 受信種別の CONFIG を「ボードの応答」と誤読 | ブロードキャストで送ると自分にも返ってくる。送信元IPで区別する |
| ファイアウォール(Windows) | Pythonテストが受信できないのを「経路の問題」と誤読 | 受信の許可ルールは**実行ファイル単位**。python.exe にルールが無ければ落ちる。Viewer には有る |
| **再ビルド直後の初回起動**(Windows) | 最初の7秒ボードから何も返らず、「ARP学習が効いていない」「Wi-Fi併用でブロードキャストが逃げた」と2つ誤診した | 新しい実行ファイルには**ローカルネットワーク通信の許可ダイアログ**が出る。許可するまで通信できない=数秒待たされるのが正常。判定するなら2回目の起動で見る |
| 他マシンでの確認中に購読した | 相手側が `waiting for stream` になり、原因を延々と誤って探した | **購読先はボードに1つだけ**。他マシンで確認している間は絶対に購読しない |
| `clocks/line`(TVP reg 39h:3Ah)の単位 | 1820でロックしているのに410と出て「H-PLLが外れている」と誤報した(判定式を書いた本人が踏んだ) | **DATACLKではなく内部基準クロック(約6.5MHz)で数えている**。`fH = 基準 / clocks per line` なので 6.44M/15699 = 410 が正解。H-PLLのロックは `pll_divide × fH` がDATACLKになるかで見る |
| CONFIGのユニキャストが届かない | 新しく焼いたファームで全キーが「応答なし」になり、**書き込みが失敗したと誤診**した | ボードとPCでサブネットが違うと、ユニキャストはデフォルトゲートウェイへ流れて着かない。`--board 255.255.255.255` なら通る。`discover` はL2ブロードキャストなので動いてしまい、勘違いを誘う(`cfg.py` の docstring に既出。**書いてあったのに踏んだ**) |
| 新旧ファームの判定に対照を取らなかった | 「新キーが応答しない=旧ファームが動いている」と結論したが、**旧キーも応答していなかった**(=通信の問題) | 「新しい機能が無い」を主張するときは、**必ず既存の機能が応答することを同時に示す**(陽性対照) |

いま残してある道具は自己検算を持たせてある。`span_check.py` は起動時に
`算術の自己検算: OK` を出す。

### 合わせ込みは既知の点を2つ以上使う(1つだと符号の誤りが「オフセット」に化ける)

NTSC復調で V(R-Y)軸の符号を逆に書いていた。**1色だけで合わせていたら、
「色相オフセットが要るのだな」で片付いて気づけなかった。**

実際に踏んだ手順(2026-08-14):

1. PS2起動画面の ○=赤 / △=緑 という**既知の2色**に対し色相を掃引した
2. どの回転でも**両方は同時に合わなかった**。2色の開きが 149.8°(本来240°)
3. **回転では2色の開きは変わらない**ので、これは回転で説明できない誤り
4. V を反転すると開きが 200.4° になり、○の誤差も -85.7° → -1.0° に落ちた

一般化すると: **回転(オフセット)は「点の間の関係」を変えない。** だから
関係が合わない時点で、オフセットでは直らない種類の誤りが確定する。1点しか
無いと必ずオフセットで合ってしまい、誤りが隠れる。

回帰試験(`tests/test_ntsc.py`)は合成信号で**必ず6色**を通し、さらに
「符号を逆にした信号ではどう回しても合わない」ことまで確かめる
(そこまでやらないと、常にPASSする無意味な試験になっていても気づけない)。

### syncdet(TVP reg 14h)は「信号が来ているか」の判定に使えない

実測(2026-08-14)。**何も繋がっていない SOGIN_1 / SOGIN_2 を選んでも、
`syncdet` は SOGD=1 / AHS=1 / AVS=1(=0x6D)を返す。** 浮いた入力で
SOGスライサが自己発振するためと思われる。これを信号の有無に使うと必ず誤判定する
(実際、コンポジットが繋がっているのに「msx」と自動判定した)。

使えるのは **fH(key 0x58)の安定性**。同じ実測:

```
SOG=_1 未接続       fH = 28309 → 29529 Hz   単調に漂う
SOG=_2 未接続       fH = 29766 → 30734 Hz   単調に漂う
SOG=_3 コンポジット fH = 15734 → 15733 Hz   収束して動かない
```

未接続は「範囲外の値をゆっくり漂う」、本物は「規定値に収束して動かない」という形で
必ず分かれる。**2回読んで一致するか**を見ればよい。入力MUXを切り替えてから
fH が落ち着くまで**約3秒**かかる。

そして**陰性対照を必ず取ること**。`videoin auto` は未接続のはずの SOGIN_1 を
先に測り、そこが「安定」と出たら判定を中止する。判定器が壊れているときに
それらしい答えを返す方が、答えないより悪い。

### チャネルに同期パルスが本当に載っているかを確かめる方法

「絵は出ているのに同期が無い」ように見えるとき、クランプの効き方を疑うのか
信号そのものが無いのかを、オシロ無しで切り分けられる。

**クランプ窓(reg 05h/06h)を動かして、基準がどう動くかを見る。**

    clamp_start=230(バースト後のバックポーチ)  → バックポーチが基準レベルに座る
    clamp_start=50 (同期チップの上)             → 同期チップが基準レベルに座る

本物の同期パルスがあれば、この2条件で**同期チップ域とバックポーチ域の差が
40 IRE ぶん(粗ゲイン0.5倍なら約37コード)入れ替わる**。信号に同期が無ければ
どちらも同じ値のままで、差はノイズぶん(数コード)しか動かない。

クランプはDCレベルを動かすだけでライン内のAC成分を消さないので、
**「ブランキング期間が数コード以内でフラット」なら、その時点で同期もバーストも
その信号には載っていない**と断定してよい。

## 原因の段を挟み込む(3段の窓)

行欠けの原因特定に効いた手法。データが通る各段に窓を作り、同じ行の値を突き合わせる。

```
pixドメイン(key 0x32)  push した瞬間の ln_first/ln_last の生値
FIFO出口  (key 0x34)  pop した瞬間の先頭の {row, x_lo, x_hi}
電線                   実際のパケットの offset_px/count_px
```

このときの結果は「pixは正しい / FIFO出口も正しい / 電線だけ違う」で、**原因の段が
一意に決まった**。片方だけ見ていると、どちらがずれているのか永久に決まらない。

## 行欠け/横ずれの原因(解決済み)

症状は2つに見えていたが原因は1つだった。

- 当初: 全幅の明るい横線の直後3行が2サンプル早く取り込まれる(横ずれ)
- 範囲計算の整合性を直した後: 全黒行の直後の数行がまるごと欠ける

原因は**送信側でヘッダの値の取り方が揃っていなかったこと**。

```
row / ts / frame  送出開始時にFIFO先頭から直接スナップショット
offset_px         先頭を毎サイクル追いかける2段レジスタ経由  ← これ
```

両者が同じFIFOエントリを指す保証がなく、範囲だけが `fifo_depth` ライン遅れて乗って
いた(depth 4→4ライン、8→8ライン の2点で確認)。内容のある行が空(`count_px=0`)で
送られれば行が欠け、隣の行の範囲が付けば絵が横にずれる。

**修正**: 範囲も row/ts と同じ瞬間に先頭からラッチし、派生値(断片数・長さ)は次の
サイクル(FSMの `LPREP` 状態)でそのラッチ値だけから作る。同一エントリ由来が構造的に
保証される。組合せ経路を短く保つための段分けは維持した(組合せで作ると sys が
42.4MHz まで落ちた実績がある)。

**教訓**: 同じエントリから来るべき値を別の経路で取ってはいけない。段を分けるなら
「どの段のどのエントリから出た値か」を揃える。パイプラインの深さを合わせるだけでは
足りず、**同じ読み出し操作から取る**必要がある。

## 否定された筋(記録)

同じ道を二度通らないために残す。いずれも実測で否定した。

- **DATACLKの位相 / H-PLL / 電源(VCOのsupply pushing)**
  LINEパケットの `ts` から `offset_px` を引いた隣接差が**全524箇所で htotal と一致**。
  HSOUTとDATACLKの関係は1行も動いていない。**基板の設計変更は不要**。
  当初 TODO で最有力候補としていた筋で、PCB の電源分離を疑ったが、そちらではなかった。
- **メタFIFOの溢れ**: 動作中の `cap_drops` は0。送出は最悪(全ライン送信)でも
  ライン周期1587サイクルのうち562サイクルしか使わない。
- **面(face)の追い越し**: `nface` を8→16にしても症状は変わらない。
- **キャプチャの非黒判定**: pixドメインの窓で、push 時点の値が内容と完全一致。
- **受信側の配置**: `assembler.rs` は `offset_px` を行ごとに絶対位置として反映している。
- **`recv_from` の syscall律速**: 「受信スレッドが27000パケット/秒に届かない」と見て
  いたが違った。NICの受信リングが既定256で溢れていただけで、2048にしたら
  35,600 pkt/s を lost 0.0013% で捌く。詳細は下の「受信の取りこぼしは…」を参照。

## nface / fifo_depth をなぜ既定のままにするか

`nface=8` / `fifo_depth=4`(`assert nface >= fifo_depth + 2`)。行欠けを追う過程で
16/8 に振ったが、原因は別だったので大きくする理由が無い。

深くしない方がよい理由:

- 実測で耐性が要る場面が無い。通常モードも全ライン送信モードも `cap_drops` は0
- 滞留が深いほどキャプチャ→送出の遅延が増える
- **滞留が深いほど「別エントリを参照する」種類のバグの被害が大きくなる**。実際、
  depth を深くしたら症状が4ライン→8ラインに悪化した。浅い方が異常に気づきやすい

将来深くする必要が出たら、根拠は `cap_drops`(key 0x33)で測れる。

## 受信の取りこぼしは NIC の受信リングだった(解決 2026-08-10)

**PC側の準備として必須**: Windows の Intel NIC は `受信バッファー`(受信記述子リング)の
既定が **256** で、これが RetroCastX のパケットレートに全く足りない。

    Set-NetAdapterAdvancedProperty -Name 'イーサネット' -RegistryKeyword '*ReceiveBuffers' -RegistryValue 2048

256 → 2048 にしただけの実測(同じ機械・同じ線・同じビットストリーム):

    間引き2(1/3, 102Mbps) / 受信バッファー 256   lost 1.7%      audio underruns 576
    間引き0(等倍, 316Mbps) / 受信バッファー 2048  lost 0.0013%   audio underruns 0
                                                 (23 / 1,727,115、約35,600 pkt/s)

**`SO_RCVBUF` を大きくしても効かない理由**: 捨てているのはソケットバッファではなく
**その手前のNICドライバのリング**。64MBのソケットバッファはリングの下流なので、
リングで溢れた分には触れない。256エントリは 35,600 pkt/s では**約7ms分**しかない。

**層を決める測り方**(これで一発で分かる):

    Get-NetAdapterStatistics -Name 'イーサネット' | fl ReceivedDiscardedPackets,ReceivedPacketErrors

| 見えたもの | 意味 |
|---|---|
| errors ≒ 0 かつ **discards が大きい** | フレームは正しく受けたが置き場所が無い = **リング溢れ**(このケース。7 と 220,680) |
| errors が増える | 物理層/ケーブル/リンク速度 |
| どちらも0なのに lost が出る | アプリまで届いている = ソケットバッファか受信スレッド。`netstat -s -p udp` の受信エラーを見る |

**「間引き」は対策になっていなかった。** 落ちるのはバーストで起きるので、平均帯域を
1/3にしてもリングは溢れる(実際 102Mbps でも 1.7% 落ちた)。等倍に戻してよい。

**否定された筋**: 「`recv_from` が27000回/秒に届かない(syscall律速)」は誤りだった。
リングを増やしたら 35,600 pkt/s を取りこぼしなく処理できている。受信スレッドを
複数にする案・キュー操作をまとめる案は**不要**。

## 実機を動かすときの準備

### ビットストリームは SRAM とフラッシュで別物

    openFPGALoader -c cmsisdap file.bit                 SRAM。電源で消える
    openFPGALoader -c cmsisdap --write-flash file.bit    SPIフラッシュ。残る

SRAMにしか書かずに作業を続けると、ボードの電源が入り直した時点で**フラッシュに
入っている古いビットストリームに戻る**。実際これで修正済みの不具合が再発し、
同時にネットワークも切れていたためネットワークだけの問題と誤診した。
実機で確認したい変更は、確認が済んだらフラッシュに書く。

### Viewer は宛先を指定せずに起動する

`--board` を付けない(既定)と SUBSCRIBE をブロードキャストで送る。ボードは
SUBSCRIBE の**送信元アドレスとポート**を覚えてそこへ返すので、Mac 側に
ボードのサブネットのアドレスは要らない。

    ./target/release/retrocastx-viewer          ← これだけでよい

`--board 192.168.10.50` を付けるとユニキャストになり、Mac に 192.168.10.0/24 への
経路が必要になる。`ifconfig en0 alias 192.168.10.1 ...` はそのための細工だが、
`ifconfig` は永続しないので Mac を再起動するたびに消える。**指定しなければ不要。**
ユニキャスト指定で3秒間応答が無ければ、Viewer はブロードキャストへ自動で落ちる
(逆に昇格はしない。宛先サブネットへの経路が必要になるため)。

なぜサブネットが違っても届くのか、と**どこまで成り立つのか**:

`LiteEthUDPIPCore` は `netmask`/`gateway_ip` を持つが既定は `None` で、このSoCも
渡していない。無効なら宛先IPを**そのままARPで引く**(`liteeth/core/ip.py:167-173`)。
だから同じL2セグメントに持ち主がいれば届く……**相手がARPに応答すれば**。

**ここがOSによって違う。** macOS/BSD は、送信元が別サブネットのARP要求にも応答する。
**Windows は応答しない**(strong host model)。そのため

    Mac(192.168.11.21)   ← ボードのARPに応答する    → 動く
    Windows(192.168.11.35) ← 応答しない              → ボードは送れない

**macOS だけで検証するとこの違いを見落とす。** 実際、design-notes に
「LiteEth にサブネットマスクもゲートウェイも無いのでサブネットが違っても届く」と
断定して書いてしまい、Windows で数時間迷った。

間にルータがある場合も成立しない(ルータはARPを転送しない)。

### ボードのARPキャッシュは2エントリしかない

`LiteEthUDPIPCore(..., arp_entries=1, ...)` が既定で、`LiteEthARPCache` は
`max(entries, 2)` なので実質2エントリ。この環境では3つのIPが関わる:

    192.168.10.1    ANNOUNCE の既定宛先(HOST_IP)
    192.168.11.21   Mac
    192.168.11.35   Windows

**2エントリで3つを回すので常に追い出しが起きる。** しかも Windows は再学習のための
ARPに応答しないので、一度追い出されると復帰しない。「さっきまで動いていたのに
動かなくなった」「電源を入れ直しても直らない」という捉えにくい形で出る。

いまは前段に学習した表(`ArpLearner`、次節)が入り、そこで答えられる相手はこの
キャッシュまで来ない。本物のキャッシュに残るのは**こちらから先に送る相手**
(ANNOUNCE の初期宛先など)だけなので、`arp_entries=4` にしてある。

**当座の回避(2026-08-10まで使っていた。いまは不要)**: Windows 側にボードと同じ
サブネットのアドレスを足す。同一サブネットになればARPが素直に成立する。

    New-NetIPAddress -InterfaceAlias 'イーサネット' -IPAddress 192.168.10.35 -PrefixLength 24

これを消すときの注意: **手動アドレスを足すとインターフェースがDHCPを使わなくなる**
ことがある。実際、消したあと DHCP が取れず 169.254 になった。
`Get-NetIPInterface -InterfaceAlias 'イーサネット' | fl Dhcp` で確認し、
必要なら `Set-NetIPInterface -InterfaceAlias 'イーサネット' -Dhcp Enabled`。

**本筋の対策(実装済み・Windows実機で確認済み 2026-08-10)**: 受信したパケットから
相手のMACを学習する。次節を参照。**この回避は不要になった。**

### 受信パケットからMACを学習する(gateware/retrocastx_net.py)

こちらへ向けて来たパケットの「イーサネット送信元MAC + IPヘッダの送信元IP」を覚え、
宛先MACの解決にそれを使う。**SUBSCRIBE を受けた瞬間に相手のMACが分かるので、ARPの
往復自体が不要になる。** 相手がARPに応答しない環境でも返せる。

**どこに挟んだか。** LiteEthのARPキャッシュ(`LiteEthARPCache.update`)へ流し込む
のが素直に見えるが、この口は `LiteEthARPTable` のFSMが既に駆動しているので外から
足せない(migenの多重ドライバ)。キャッシュ自体も学習の置き場所に向かない:

- 書き込みがラウンドロビンで、同じIPを畳まない。同一IPの重複エントリができ、検索は
  先に見つかった側(=古いMAC)を返しうる
- 1秒ごとに全消去する。ただし消去タイマは**検索でもリセットされる**ので、映像が
  流れている間は実質消えない ─ 「消えるときだけ消える」読みにくい挙動になる

そこで **IP TX から見た「ARPテーブル」の位置に自前の表(`ArpLearner`)を差し込んだ**。
学習済みなら即答し、未知なら本物のARPテーブルへ委譲して応答を中継する。表は4エントリ、
IPで畳む(同じIPならMACだけ更新)。LiteEth本体は無改造 ─ `gateware/litex-src` は
`litex_setup.py` で取ってくるものでリポジトリに入っておらず、パッチを当てても残らない。
そのため `LiteEthUDPIPCore` の構成(MAC + ARP + IP + ICMP + UDP)だけを
`RetroCastXUDPIPCore` として持ってきている。

**何から学習するか(絞る理由)。** `LiteEthIPRX` は `with_broadcast=True` で宛先IPを
問わず通すので、そのまま学習させるとLANのブロードキャスト/マルチキャスト
(mDNS/SSDP/NetBIOS)で狭い表が埋まり、肝心の購読者が追い出される。学習するのは
**こちらへ向けられたものだけ**に絞ってある:

    自IP宛のIPパケット          ping等も含む(ICMP応答もARP無しで返せる)
    自UDPポート宛のUDPパケット   SUBSCRIBE/CONFIG。既定ではブロードキャストで来る
    自IP宛のARP                 LiteEthARPRX が自IP宛だけを通す

**組合せ経路にしてはいけない。** 学習の出力を組合せでARPの表につなぐと
「IPヘッダのレジスタ → ICMP/UDPのデコード → UDP RXのFSM → 表の比較 → 書き込み
イネーブル」が1サイクルの経路になり、実測22.9ns(sys 45MHz = 22.2ns に対し未達、
nextpnr 43.6MHz)。**1段レジスタを挟んで解決**(sys 54.7MHz PASS、
LUT4 11196 = 46%、DFF 6737 = 27%。レジスタを挟んだ方がLUTも減った)。
学習が1サイクル遅れても誰も困らない。**論理を足したら sys のクリティカルパスを
見る** ─ 範囲計算の段分け(42.4MHz)、CONFIG応答の If/Elif 連鎖(38〜44MHz)に続く
3例目。いずれも「受信/設定の経路から広いマルチプレクサや比較器へ組合せで入る」形。

**検証**: `gateware/sim_arp.py`(実機不要)。応答しないARPテーブルを差し込んで
「相手がARPに応答しない」状況を再現し、SUBSCRIBE相当を1つ受けるだけでARPを一度も
引かずにユニキャスト解決できること、IPで畳むこと、溢れたら古い順に使い回すこと、
本物のARPの応答待ち(最悪800ms)の間も学習を取りこぼさないことを確認している。

**simの範囲外**: RXへのタップ(`ip.rx` / `udp.rx` / `arp.rx`)はスタブで置き換えて
いるので、LiteEthの実際の信号の並びまでは確かめていない。根拠は「Depacketizer は
ヘッダを `sr` に載せたままパケット分保持し、ヘッダ由来のフィールドはそこから
組合せで出る」というLiteEthの実装(`liteeth/packet.py`)で、ビルドが通ることで
属性名の存在は確認できる。**ここが違っていたときの症状は key 0x40 が増えないこと。**

**実機の結果(2026-08-10)。これで確認できたと言える根拠**:

Windows(`イーサネット` に `192.168.11.35/24` だけ。`192.168.10.35` は削除済み =
ボードとは別サブネット)から Viewer を `--board` なしで起動し、**532フレーム /
55.5fps / 314〜363Mbps / lost 1.1% / orphan 0 を受信**(起動から1秒以内に開始。
`--headless 10`)。そのときボードのカウンタは

    表で即答  (0x41)   1,437 → 579,334   約58万回
    ARPへ委譲 (0x42)       5 →       5   **1回も増えていない**

`0x42` が動かないことが決め手。Windows のMACをARPで引く必要があったなら必ず 0x42 が
増え(そして応答が無いので失敗し)、映像は出ない。ANNOUNCE のユニキャスト返信
(`INFO=1`)が届いているのも同じことを示す。Mac(192.168.11.21)からも同様に確認。

**読み方の注意**: `0x43`(最後に学習した相手)は診断ツール自身のパケットで上書き
される。Macから読むと必ず自分が見える。**判定に使うのは 0x41/0x42 の増減**。

**診断カウンタの読み方**: `python3 -m retrocastx.arp_check`

    key 0x40  学習した回数            増えない = 受信から学習できていない
    key 0x41  学習した表で即答した数   増える   = 学習した表で解決している
    key 0x42  本物のARPへ委譲した数    **購読中に**増え続けるなら学習が効いていない
    key 0x43  最後に学習した相手のIP
    key 0x44/0x45  同 MAC(下位4B / 上位2B)

0x42 は購読前でも増える(下記のANNOUNCEの初期宛先を毎秒引き直すため)。見るのは
**購読して映像が流れている間に増え続けないか**。

そもそも応答が1つも返らなければ、それが症状そのもの(受信はできているのに返せて
いない)。

**GETはまとめて投げない。** ボードのCONFIG応答は「1つ分の保留」しか持たない
(`cfg_pending` と `cfg_key`/`cfg_reply_val` が1組)。6キーを連続で投げると応答が
上書きされて落ちる ─ 実機で6キー中1つだけ返らない形で出た。`arp_check` は1キーずつ
送って応答を待ち、返らなかったキーだけ再送する。**他の診断ツールも同様**。

なお **ANNOUNCE の初期宛先 `192.168.10.1` は誰も応答しないことがあり**、
その解決は8回×100ms=最悪800msかけて失敗する。この間IP TXは止まるが、購読前なので
映像には影響しない(SUBSCRIBE を受けた時点で ANNOUNCE の宛先は送信元へ切り替わる)。

帯域の心配は要らない。ブロードキャストになるのは Viewer が送る側だけ。

    SUBSCRIBE(keepalive)   Viewer→ボード  ブロードキャスト  約40B × 0.5回/秒
    CONFIG                 Viewer→ボード  ブロードキャスト  操作時だけ
    MODE / LINE / AUDIO    ボード→Viewer  **ユニキャスト**   約500Mbps

映像はユニキャスト(`retrocastx_stream.py` の `dst_ip, sub_ip`)なので、スイッチは
MAC学習によりMacのポートにしか流さない。

**未対応の懸念**: `255.255.255.255` をどのインターフェースから出すかはOSが選ぶ。
Wi-Fiと有線が両方有効な環境では、ブロードキャストがWi-Fi側へ出てボードに届かない
可能性がある(いまはソケットを `0.0.0.0` に束縛しOS任せ)。実害が出たら、
インターフェースごとに送信元アドレスを変えて総当たりし、応答があったものを使う
形にする。有線1本の環境では問題にならないので後回しにしている。
**まだ実害は観測していない**(2026-08-10に「Wi-Fi併用のせいで最初の7秒出なかった」
と一度誤診したが、原因は再ビルド直後の許可ダイアログだった。下の表を参照)。

### 「届いていない」と「捨てている」を分ける

ボード→受信機が成立しないとき、どちらなのかを数字で決める手順。

| 見るもの | 分かること |
|---|---|
| NICの受信バイト増分(`Get-NetAdapterStatistics`) | 増えないなら**ボードが送っていない**。増えるのに絵が出ないなら受信側が捨てている |
| `Get-NetNeighbor <board> \| Select State` | 消してから復活しないなら**ボードがARPを投げていない**(=購読を認識していない) |
| 受信種別の内訳(frames==0 のとき出る) | 自分のブロードキャストが自分に返ってきているだけ、というのが見える。これをボードの応答と読み違えた |
| 旧コミットを**同じexeのパス**でビルドして比較 | 自分のコードが原因かを切り分ける。パスを変えるとファイアウォールのルールが変わって交絡する |

`lost` は「届いたパケットのseqの飛び」から数えるので、**何も届いていないときは 0 になる**。
`lost=0` を「ロスが無い」と読んではいけない。

### 購読先はボードに1つしかない

`sub_ip`/`sub_port` は1組だけ。Viewer と測定ツールを同時に動かすと購読先を
取り合い、後から SUBSCRIBE した方に映像が向く。測定するときは Viewer を閉じるか、
ツール側で別のローカルポートを使う(`span_check --local-port`)。

## 全ライン送信(key 0x30)

非黒範囲の最適化を切って1ラインまるごと送る。診断用に入れたが実用の逃げ道にもなる。

- 帯域は htotal 画素ぶん。31kHz(htotal 1104)で約555Mbps、GbEに収まる
- 範囲判定を通らないので、範囲まわりの不具合を切り離せる
- Viewer のチェックボックスから切り替えられる

## pll_divide をドットクロック候補から決める

絵の内容から探す方法(スペクトル占有率、鮮鋭度の山登り)は、真っ黒な画面や模様の
無い画面で当たらない。信号だけで決める方がよい。

```
htotal = f_dot / fH
```

レトロPCのドットクロックは水晶を分周した有限個の値しか取らないので、`f_dot` に候補を
入れて整数になるものを選べば決まる。`fH` は pll_divide に依存しない絶対値として
測れている(sysドメインで1秒間エッジを数える)。誤差 ±1Hz は、31.5kHz・htotal 1104 で
**htotal の ±0.035カウント**にしかならない。

X68000 は水晶2つ(69.55199MHz / 38.86363MHz)の分周で全帯域が説明できた。

| fH | ドットクロック | htotal |
|---|---|---|
| 31.499kHz | 69.55199/2 = 34.776MHz | 1104 |
| 24.699kHz | 69.55199/2 = 34.776MHz | 1408 |
| 15.980kHz | 38.86363/2 = 19.432MHz | 1216 |

**選び方に落とし穴がある。** 正しい htotal の約数はすべて整数になる(1104が正解なら
552も276も整数)。しかも残差[カウント]は htotal に比例するので、残差最小で選ぶと必ず
小さい方へ落ちる(実際 31.5kHz で552、24.7kHz で704を選んでしまった)。

正しい選び方は2段:

1. **相対誤差**(残差/htotal)で水晶を特定する。同じ水晶の分周違いは相対誤差が揃う
   (実測 3.2e-5)、別の水晶は桁で外れる(1.6e-4)
2. その一族の中で**ラインバッファに収まる最大**を採る。真の htotal より小さいと
   ドットを取りこぼす(破壊的)が、大きいのは整数倍オーバーサンプルで無害なので、
   迷ったら大きい側へ倒す

実装は `client/src/profiles.rs`(Viewer)と `host/python/retrocastx/profiles.py`。
上の3帯域は Rust 側の回帰テストに入れてある。VGA / PC-9801 のプロファイルは
**数値の裏を取っていない**(コードにも【未検証】と明記)。

## 診断用CONFIGキー

| key | R/W | 内容 |
|---|---|---|
| 0x30 | R/W | 全ライン送信(0=通常 / 1=1ラインまるごと) |
| 0x31 | R/W | 範囲を調べたいスロット番号 |
| 0x32 | R | そのスロットの `{ln_any, ln_last, ln_first}`(push時点、pixドメインの生値) |
| 0x33 | R | `cap_drops`(push時にFIFOが満杯だった回数。16bitで折り返す) |
| 0x34 | R | pop した瞬間のFIFO先頭の `{row, x_hi, x_lo}` |
| 0x2A/0x2B/0x2C | R | 生同期の fH[Hz] / fV[mHz] / VSYNC間のライン数 |
| 0x40/0x41/0x42 | R | ARP学習: 学習した回数 / 学習した表で即答した数 / 本物のARPへ委譲した数 |
| 0x43/0x44/0x45 | R | ARP学習: 最後に学習した相手のIP / MAC下位4B / MAC上位2B |

0x40..0x45 は `python3 -m retrocastx.arp_check` で読む。

## mflags bit0 は「インタレースかどうか」ではない(2026-08-14)

`mflags bit0` の意味は **「スロットが vtotal 個 = フレーム単位の織り込み」** で、
ゲートウェアでは `stat_interlaced.eq(capture.il_slot1)` から来る。
**VSYNCがフィールドごとに来る本物のインタレースでは 0 になる。**

これを Viewer が「インタレースではない」と読んでいて、2つ壊れていた:

1. **太らせ(隙間を隣の行で埋める処理)が動いて、織り込みを毎フィールド壊していた。**
   埋まっているのは奇数行だけなので、偶数行2は「上(1)も下(3)も埋まっている」判定に
   なり行1が複製される。次のフィールドでは逆向きに上書きされる。つまり各行が
   「本物の内容」と「隣の行のコピー」をフィールドレートで往復する。
   **拡大すると同じラインに縞が交互に出てチラチラ見える**という形で出た
2. 欠損減衰(0.8)が半分の行に毎フィールド掛かる設定になっていた
   (1で全行が埋まってしまうので実際には出番が無かったが、太らせを止めると効く)

### パリティ単体では判定できない

ボードは行位置を「フィールド内の行×2 + 極性」で送るので、**プログレッシブでも
1つ飛びに埋まる**。違いはフレーム間の挙動:

    プログレッシブ  極性が固定 → パリティが**常に同じ**
    インタレース    フィールドごとに反転 → パリティが**交互**

なので `FrameAssembler` は**パリティの交互性を数えて**判定する
(非対称に増減させ、途切れたら早く抜ける)。「インターレースは設定ではなく
測定で決まる」という既存の方針と同じ形。

### 直ったことの確認方法

    修正前  未充填の行 2     (太らせが261行を複製で埋めていた)
    修正後  未充填の行 263   (= 526の半分。残りは前フィールドの内容 = 織り込み)

    完全一致する隣接行 0%   (複製していれば約50%になる)
    隣接行の平均絶対差  1行差 7.58 < 2行差 8.29

**最後の不等号の向きに注意。** 行 N と N-1 は別フィールド=画面上で隣接なので似る。
行 N と N-2 は同じフィールドで2ライン離れているので似ない。
つまり **1行差 < 2行差 が織り込み成立の印**で、逆ではない(一度取り違えた)。
