## 測定系を先に疑う

このプロジェクトで何度も同じ形で止まった。**「効かない」「壊れている」という観測は、
測定系の欠陥でも全く同じ形で出る。** 実測値を根拠に議論する設計なので、道具が間違って
いると全部が狂う。

実際に踏んだもの:

| 落とし穴 | 症状 | 正しい理解 |
|---|---|---|
| LINEパケットの `ts` の定義 | 隣接行の差が htotal にならず「同期が動いている」と誤読 | `ts` は**ライン先頭 + offset_px**(断片ごとに正しいサンプル時刻を持たせるため)。比べるなら offset を引く |
| entry 変換の式 | 全行が不一致に見えた | `offset_px`/`count_px`[画素] → entry(2画素)は、末尾が `(offset + count - 1)//2` |
| SIMの `hs_offset` | 全画素が1ずれ、不具合と誤認 | RGBは1段・HSOUT/VSOUTは2段のレジスタで受けるので、駆動側が置いた画素と取り込みの x に固定のずれがある。SIMでは `hs_offset=1` で打ち消す |
| A/B比較の交絡 | 「範囲が FIFO段数ぶん遅れる」という誤った結論 | 全ライン送信モード(key 0x30)は送出負荷が60倍違い、FIFOの滞留状態が変わる。**同条件を2回取った自己一致率**を先に出して、ばらつきの下限を示すこと |
| `cap_drops` の読み方 | 42289という値を見て「FIFOが溢れている」と誤読 | 購読していない間は誰もFIFOを抜かないので当然溢れる(92.4%)。**動作中は0**。読むなら購読しながら時間差で2回 |

いま残してある道具は自己検算を持たせてある。`span_check.py` は起動時に
`算術の自己検算: OK` を出す。

## 原因の段を挟み込む(3段の窓)

行欠けの原因特定に効いた手法。データが通る各段に窓を作り、同じ行の値を突き合わせる。

```
pixドメイン(key 0x32)  push した瞬間の ln_first/ln_last の生値
FIFO出口  (key 0x34)  pop した瞬間の先頭の {row, x_lo, x_hi}
電線                   実際のパケットの offset_px/count_px
```

このときの結果は「pixは正しい / FIFO出口も正しい / 電線だけ違う」で、**原因の段が
一意に決まった**。片方だけ見ていると、どちらがずれているのか永久に決まらない。

## 行欠け/横ずれの原因(解決済み)

症状は2つに見えていたが原因は1つだった。

- 当初: 全幅の明るい横線の直後3行が2サンプル早く取り込まれる(横ずれ)
- 範囲計算の整合性を直した後: 全黒行の直後の数行がまるごと欠ける

原因は**送信側でヘッダの値の取り方が揃っていなかったこと**。

```
row / ts / frame  送出開始時にFIFO先頭から直接スナップショット
offset_px         先頭を毎サイクル追いかける2段レジスタ経由  ← これ
```

両者が同じFIFOエントリを指す保証がなく、範囲だけが `fifo_depth` ライン遅れて乗って
いた(depth 4→4ライン、8→8ライン の2点で確認)。内容のある行が空(`count_px=0`)で
送られれば行が欠け、隣の行の範囲が付けば絵が横にずれる。

**修正**: 範囲も row/ts と同じ瞬間に先頭からラッチし、派生値(断片数・長さ)は次の
サイクル(FSMの `LPREP` 状態)でそのラッチ値だけから作る。同一エントリ由来が構造的に
保証される。組合せ経路を短く保つための段分けは維持した(組合せで作ると sys が
42.4MHz まで落ちた実績がある)。

**教訓**: 同じエントリから来るべき値を別の経路で取ってはいけない。段を分けるなら
「どの段のどのエントリから出た値か」を揃える。パイプラインの深さを合わせるだけでは
足りず、**同じ読み出し操作から取る**必要がある。

## 否定された筋(記録)

同じ道を二度通らないために残す。いずれも実測で否定した。

- **DATACLKの位相 / H-PLL / 電源(VCOのsupply pushing)**
  LINEパケットの `ts` から `offset_px` を引いた隣接差が**全524箇所で htotal と一致**。
  HSOUTとDATACLKの関係は1行も動いていない。**基板の設計変更は不要**。
  当初 TODO で最有力候補としていた筋で、PCB の電源分離を疑ったが、そちらではなかった。
- **メタFIFOの溢れ**: 動作中の `cap_drops` は0。送出は最悪(全ライン送信)でも
  ライン周期1587サイクルのうち562サイクルしか使わない。
- **面(face)の追い越し**: `nface` を8→16にしても症状は変わらない。
- **キャプチャの非黒判定**: pixドメインの窓で、push 時点の値が内容と完全一致。
- **受信側の配置**: `assembler.rs` は `offset_px` を行ごとに絶対位置として反映している。

## nface / fifo_depth をなぜ既定のままにするか

`nface=8` / `fifo_depth=4`(`assert nface >= fifo_depth + 2`)。行欠けを追う過程で
16/8 に振ったが、原因は別だったので大きくする理由が無い。

深くしない方がよい理由:

- 実測で耐性が要る場面が無い。通常モードも全ライン送信モードも `cap_drops` は0
- 滞留が深いほどキャプチャ→送出の遅延が増える
- **滞留が深いほど「別エントリを参照する」種類のバグの被害が大きくなる**。実際、
  depth を深くしたら症状が4ライン→8ラインに悪化した。浅い方が異常に気づきやすい

将来深くする必要が出たら、根拠は `cap_drops`(key 0x33)で測れる。

## 全ライン送信(key 0x30)

非黒範囲の最適化を切って1ラインまるごと送る。診断用に入れたが実用の逃げ道にもなる。

- 帯域は htotal 画素ぶん。31kHz(htotal 1104)で約555Mbps、GbEに収まる
- 範囲判定を通らないので、範囲まわりの不具合を切り離せる
- Viewer のチェックボックスから切り替えられる

## pll_divide をドットクロック候補から決める

絵の内容から探す方法(スペクトル占有率、鮮鋭度の山登り)は、真っ黒な画面や模様の
無い画面で当たらない。信号だけで決める方がよい。

```
htotal = f_dot / fH
```

レトロPCのドットクロックは水晶を分周した有限個の値しか取らないので、`f_dot` に候補を
入れて整数になるものを選べば決まる。`fH` は pll_divide に依存しない絶対値として
測れている(sysドメインで1秒間エッジを数える)。誤差 ±1Hz は、31.5kHz・htotal 1104 で
**htotal の ±0.035カウント**にしかならない。

X68000 は水晶2つ(69.55199MHz / 38.86363MHz)の分周で全帯域が説明できた。

| fH | ドットクロック | htotal |
|---|---|---|
| 31.499kHz | 69.55199/2 = 34.776MHz | 1104 |
| 24.699kHz | 69.55199/2 = 34.776MHz | 1408 |
| 15.980kHz | 38.86363/2 = 19.432MHz | 1216 |

**選び方に落とし穴がある。** 正しい htotal の約数はすべて整数になる(1104が正解なら
552も276も整数)。しかも残差[カウント]は htotal に比例するので、残差最小で選ぶと必ず
小さい方へ落ちる(実際 31.5kHz で552、24.7kHz で704を選んでしまった)。

正しい選び方は2段:

1. **相対誤差**(残差/htotal)で水晶を特定する。同じ水晶の分周違いは相対誤差が揃う
   (実測 3.2e-5)、別の水晶は桁で外れる(1.6e-4)
2. その一族の中で**ラインバッファに収まる最大**を採る。真の htotal より小さいと
   ドットを取りこぼす(破壊的)が、大きいのは整数倍オーバーサンプルで無害なので、
   迷ったら大きい側へ倒す

実装は `client/src/profiles.rs`(Viewer)と `host/python/retrocastx/profiles.py`。
上の3帯域は Rust 側の回帰テストに入れてある。VGA / PC-9801 のプロファイルは
**数値の裏を取っていない**(コードにも【未検証】と明記)。

## 診断用CONFIGキー

| key | R/W | 内容 |
|---|---|---|
| 0x30 | R/W | 全ライン送信(0=通常 / 1=1ラインまるごと) |
| 0x31 | R/W | 範囲を調べたいスロット番号 |
| 0x32 | R | そのスロットの `{ln_any, ln_last, ln_first}`(push時点、pixドメインの生値) |
| 0x33 | R | `cap_drops`(push時にFIFOが満杯だった回数。16bitで折り返す) |
| 0x34 | R | pop した瞬間のFIFO先頭の `{row, x_hi, x_lo}` |
| 0x2A/0x2B/0x2C | R | 生同期の fH[Hz] / fV[mHz] / VSYNC間のライン数 |
