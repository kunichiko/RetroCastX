# コンポジットビデオを3番系統(D-SUB緑 + SOGIN_3)で試す

新しいセッションで着手するための設計と手順。**この文書だけ読めば始められる**ように、
根拠(データシートの該当箇所・コードの行)を全部書いてある。

## 0. 結論の要約

- **TVP7002 はコンポジットをデコードできない。** Digitizer であって Decoder ではなく、
  色副搬送波PLL・直交復調・Y/C分離が丸ごと無い
- ただし **8fsc 線同期サンプラーとしては使える。** 復調は Viewer 側で書く
- 3番系統を使うのは、**緑→SOGタップ(`c_sog3`)があって同じ信号から digitize と
  同期抽出の両方が取れる**のが3番だけだから。SOGIN_2 は(PCB版では)CSYNC専用ピンから
  1/2分圧を経由しているので、映像そのものからの同期抽出には使えない
  — ただし **CSYNC を別線でもらう機種(MSX)の同期入力としては SOGIN_2 を使う**。
  その切り替えに reg 19h の実行時制御が要る(下記)

### Step 1〜3 は実機で通った(2026-08-14)

**コンポジットの digitize は成立している。** 実測:

```
MODE: YC8  htotal=1820  dotclk=28.6356 MHz  fH=15734.0 Hz   ← 8fsc NTSC ちょうど
       同期チップ  ブランキング  バースト p-p  映像 min..max
コード      127.0         158.0          29.0    155..220
IRE         -40.0           0.0          37.4   -3.9..79.4   (1 IRE = 0.78 コード)

バーストの周期 = 8.00 サンプル → 3.5795 MHz   ← 副搬送波ちょうど
隣接ラインの位相差 = 177°                      ← 180°= 2次元コムが成立する
```

- 同期チップとブランキングの段差が 31コード = 規格どおりの 40 IRE
- バースト 29コード p-p(§2の設計値36に対して、ゲインが実測でやや低い)
- **バーストが8サンプル/周期でサンプルされ、ライン毎に180°反転している**。
  Step 4 の位相ロックと2次元コムに必要な条件は揃った

**Step 4(デコーダ)も Viewer まで通った**(§4 Step 4)。残っているのは画質の詰めと、
色相の絶対確認のためのカラーバー映像源。

★**Viewer は YC8 のとき pll_divide を触らない**ようにした(`main.rs` の
`pll_locked_by_format`)。コンポジット/S端子のサンプルレートは規格で決まる値で、
実測で探すものではないため。止めた自動経路は3つ:

| 経路 | 何が起きていたか |
|---|---|
| 帯域(15/24/31kHz)ごとの pll_divide 復元 | 15kHz帯の保存値で 1820 が上書きされた(**これが本命**) |
| `自動調整` | 開始時に `AUTO_PLL_MAX` = **2304** を投げる |
| `send all` | 保存してある古い値を押し戻す |

実際に踏んだ: 1820 を入れた直後に 2304 へ書き換わり、副搬送波が
**10.13サンプル/周期**になっていた。**絵は普通に出るので気づきにくい**
(むしろ水平は細かく見える)。手動の `pll_div` 欄は逃げ道として残してある。

入力方式の切り替えは `retrocastx.videoin` にまとめてある:

    python3 -m retrocastx.videoin --board 192.168.10.50 apply composite
    python3 -m retrocastx.videoin --board 192.168.10.50 auto      # 方式を当てて設定
    python3 -m retrocastx.videoin --board 192.168.10.50 status    # 入力選択と同期
    python3 -m retrocastx.videoin --board 192.168.10.50 probe     # ★波形を実測して判定
    python3 -m retrocastx.videoin --board 192.168.10.50 modes     # 表を見る

`probe` が要るのは、**この段の失敗が「絵は出ているのに復調できない」形で出る**から。
ボトムレベルクランプならバーストの下半分が消え、ミッドレベルでゲインを下げ忘れると
白が飽和する。どちらも絵は出る。だから同期チップ・ブランキング・バースト振幅を
コードで読んで判定する(合成波形での回帰試験は `tests/test_videoin.py`)。

### 入力方式の切り替えは全部CONFIGで済む(焼き直し不要)

**手組みボードの配線**(排他。同時には繋がらない):

| モード | 映像 | 同期 | reg 19h | reg 0Eh |
|---|---|---|---|---|
| `x68k` | Rin3/Gin3/Bin3 | HSYNC_A / VSYNC_A | 0xAA | 0x52 |
| `msx` | Rin3/Gin3/Bin3 | **SOGin2** (CSYNC) | **0x6A** | 0x5B |
| `composite` | Gin3 (CVBS) | SOGin3 (Gin3から分岐) | 0xAA | 0x5B |
| `svideo` | Gin3=Y / Rin3=C | SOGin3 (Yから分岐) | 0xAA | 0x5B |

★**msx だけ SOG の入力ピンが違う**(SOGIN_2)。レジスタ19h は
`MUX1 = ((2 << 6) | ...)` でSOG=_3に焼き込まれた**ビルド時定数**だったので、
**ビットストリームを焼き直さないと MSX に切り替えられなかった**。
key 0x69 を足して実行時に振れるようにした。これで3方式とも CONFIG だけで済む。

HSYNC_A/VSYNC_A の選択は 19h ではなく **1Ah bit0/bit2**(key 0x5D)。混同しやすい。

### 自動判別が成立する理由

3方式は**同期がどこに来るかが違う**ので、絵の内容を見ずに判別できる:

```
生HSYNC/VSYNC(TTL)に信号がある            → x68k
SOGIN_2 で fH が安定する(19h=0x6A)       → msx
SOGIN_3 で fH が安定する(19h=0xAA)       → composite / svideo
```

最初の分岐に使う `key 0x2A`(生HSYNC周波数)は **TVPを通らない経路**を
sysドメインで1秒数えた絶対値なので、**TVPの設定に一切依存せず読める**。
これがあるおかげで「TVPを設定しないと測れない/測れないと設定できない」という
鶏と卵にならない。

★**`syncdet`(reg 14h)で判定してはいけない。** 実測では**何も繋がっていない
SOGIN_1 / SOGIN_2 でも SOGD=1 / AHS=1 / AVS=1 を返した**(浮いた入力で
スライサが自己発振する)。最初これで判定して、コンポジットを「msx」と誤判定した。
使えるのは **fH の安定性**:

```
SOG=_1 未接続       fH = 28309 → 29529 Hz   単調に漂う
SOG=_2 未接続       fH = 29766 → 30734 Hz   単調に漂う
SOG=_3 コンポジット fH = 15734 → 15733 Hz   収束して動かない
```

MUXを切り替えてから fH が落ち着くまで**約3秒**。`videoin auto` は
**未接続のはずの SOGIN_1 を陰性対照として先に測り**、そこが「安定」と出たら
判定を中止する(判定器が壊れているときにそれらしい答えを返す方が悪い)。

`composite` と `svideo` は同期の出方が同じなので同期だけでは区別できない
(C(赤ch)に信号があるかを見る必要がある = `probe` の仕事)。`auto --svideo` で指定する。

★**1Bh と 1Ch はビット割りが違う。** 1Bh は `[7:4]=Green [3:0]=Blue`、

★**19h はビルド時定数ではなくなった。** `MUX1` は初期値としてだけ残り、
実行時は key 0x69 が上書きする。これが無いと MSX(SOGIN_2)に切り替えられない。

## 2. レベル設計 — ここが当初の計画の穴だった

**ミッドレベルクランプを入れるだけでは駄目。粗ゲインを同時に下げる。**

コンポジットは 1Vpp = 140 IRE(同期 -40 〜 白 +100)。ADCフルスケール入力は
1Vpp で、粗ゲイン(1Bh)が入力を何倍してからADCへ渡すかを決める。
ミッドレベルクランプはブランキングを **512**(10bit中央)に座らせるので、
**白側に使えるのは残り512コードだけ**になる。

100%カラーバーの黄のピークは +131 IRE ある。飽和させない条件は
`131 IRE × (コード/IRE) ≤ 511`:

```
粗ゲイン  ADC FS入力  1 IRE   黄131IREの行き先   バースト40IRE p-p (8bit)
0.5 (07h) 2.00 Vpp   3.66c   512+479 =  991 ○   146c(10bit) → 36c
0.6 (17h) 1.67 Vpp   4.39c   512+575 = 1087 ×   176c        → 44c
0.7 (27h) 1.43 Vpp   5.11c   512+669 = 1181 ×   204c        → 51c
1.2 (77h) 0.83 Vpp   8.77c   同期チップから飽和 ×             ―
        ↑既定
```

→ **1Bh = 0x07(Green 0.5倍)が出発点。バーストは 36コード p-p** になる。
RGB555 の 9コードより4倍良く、往年のCVBSデコーダIC(4fsc/8bit)と同等以上。

### ★否定された別解: 粗オフセットで持ち上げる(実測で効かない)

当初「ボトムレベルクランプのまま粗オフセット(1Fh)でブランキングを持ち上げれば、
ミッドレベルにせずに済んで粗ゲインを上げられる(バースト58コード)」と書いていた。
**実測で完全に否定された。**

    0x65(reg 1Fh)を +64 → +32 → +0 → -32 と振っても、ブランキングは166のまま
    (レジスタの書き込みは読み返しで確認済み)

理由は **reg 2Dh で粗クランプが全チャネル無効(既定)** だから。緑はファイン
クランプだけで動いていて、**ファインクランプの帰還ループが ADC前に足した
オフセットを打ち消す**。粗オフセットは粗クランプの経路にしか効かない。

代わりに効いたのは**ファインゲイン(reg 09h)**だった。粗ゲインが最小(0.5倍)でも
ファインゲインが 33 = 1.129倍 掛かっていて、**白が4.6%クリップしていた**。
0 にして 0.00% になった(バーストは38→33コード)。

## 3. サンプリングは 8fsc(1820サンプル/ライン)

4fsc ではなく 8fsc にする。理由は**既存のアンチエイリアスがそのまま最適値になる**こと。

```
                サンプル/ライン  サンプルレート  ナイキスト   既存フィルタ(fc 16.8MHz)の減衰
NTSC 4fsc            910          14.318MHz     7.16MHz     -0.45dB  ← 折り返しに無防備
NTSC 8fsc           1820          28.636MHz    14.32MHz     -2.4dB   ← ちょうど良い
PAL  8fsc           2270          35.469MHz    17.73MHz     -3.5dB   ← ★バッファ2048に入らない
```

既存フィルタは 220Ω + 33pF + TVP入力容量10pF = 43pF → fc = 16.8MHz。

```
3.58MHz (副搬送波)   -0.19dB   ← クロマがフラットに通る
4.2MHz  (輝度上限)   -0.26dB
14.32MHz(ナイキスト) -2.4dB
```

- 1820 は 12bit分周(最大4095)に収まり、28.636MHz は 12〜165MHz の範囲内
- 1820 ≤ `width=2048` なのでキャプチャバッファに全ライン入る
- **PAL は 2270 > 2048 でバッファを超える。** PAL をやるなら 4fsc(1135)に落とすか
  バッファを広げる。国内の実機は 15.7kHz 系が主なので NTSC 優先で進める

## 4. 手順

### Step 1 — 配線して同期とPLLのロックを確認する ← **いまここ**

**ケーブル**: コンポジットの芯線を D-SUB15 の **pin3(G)**、シールドを **pin4(G-GND)** へ。
HSYNC/VSYNC は繋がない(SOG経路を使う)。75Ω終端は基板側の `ch_g.r_term` にある。

★**ピン番号を間違えないこと。** このコネクタは VGA の HD-15 ではなく
**X68000式の DA-15**(`Dsub15X68k`、`hardware/adc-frontend/main.ato:265`)で、
R/G/B と各GNDが交互に並ぶ:

```
pin1 = R    pin2 = R-GND
pin3 = G    pin4 = G-GND     ← コンポジット/S-VideoのY はここ
pin5 = B    pin6 = B-GND
pin7 = YS   pin8 = GND    pin10/11 = AUDIO L/R   pin14/15 = H/V SYNC
```

(この文書は当初 VGA HD-15 の配置(pin2=G / pin7=G-GND)を書いていた。誤り)

    python3 -m retrocastx.videoin --board <ボードIP> apply
    python3 -m retrocastx.videoin --board <ボードIP> status

`apply` が §1 の表の「コンポジットの値」列を全部書く。個別に振るなら
`python3 -m retrocastx.cfg --board <IP> set 0x19 0x08` のように。

チャージポンプの根拠。`ICP = 40 × KVCO / (pixels per line)`、VCO=00 なら KVCO=75:

```
pll_divide 1104 (現状)  40×75/1104 = 2.72  → 3   現在の 0x18 = VCO00/ICP3 と一致
pll_divide 1820 (8fsc)  40×75/1820 = 1.65  → 2   → 0b00_010_000 = 0x10
pll_divide 2270 (PAL)   40×75/2270 = 1.32  → 1   → 0x08
```

クランプ位置の根拠。NTSC の同期立ち下がりを起点にすると:

```
0〜4.7µs      同期チップ
4.7〜5.3µs    ブリーズウェイ
5.3〜7.8µs    カラーバースト (3.58MHz × 9周期)
7.8〜9.4µs    バースト後のバックポーチ  ← ここでクランプする
9.4µs〜       アクティブ映像
```

28.636MHz は 34.93ns/クロックなので 7.8µs=223、9.4µs=269クロック。
**start=230 / width=30 なら 230〜260(8.03〜9.08µs)** で窓の内側に入る。
**バーストの上でクランプすると基準がずれる**ので、既定の 0x32(=50クロック=1.75µs、
同期チップの上)のままでは駄目。

**SOG LPF は変更不要。** `cfg_in_mux2` の既定 0x12 は bit[7:6]=00 = **2.5MHz** で、
3.58MHz のバーストを既に落としている(15kHz機向けにそう決めてあった)。

**入力MUXも変更不要。** `MUX1`=0xAA で SOG/R/G/B すべて _3。

**確認すること**

| CONFIGキー | 期待値 |
|---|---|
| 0x54 syncdet | SOGD=1 / AHS=1 / AVS=1(**実測 0x6E**。MSXのC-SYNCと同じ値) |
| 0x55 lines/frame | 262 か 263(インタレース源なら525前後)。**実測 261** |
| 0x56 clocks/line | **1820 ではない。** 下記参照。実測 410 |
| 0x58 fH (TVP HSOUT) | 15734 Hz 付近。**実測 15699 Hz** |

★**`clocks/line`(reg 39h:3Ah)は DATACLK で数えた値ではない。** データシートは
「A known timing reference based on either the internal clock reference (~6.5 MHz)
or an external clock reference input (EXT_CLK) of up to 27 MHz」と明記していて、
換算式は

```
fH = clock reference frequency / clocks per line
```

つまり **内部基準(約6.5MHz)/ fH** が出る。8fsc(1820)でロックしていても
6.44MHz / 15699Hz = **410** になるのが正しい。当初この表は「1820前後」と
書いていたが誤りで、`videoin status` にも同じ誤りを実装してしまい、
**正常にロックしているのに「H-PLLが外れている」と誤報した**。

H-PLLがロックしているかは **`pll_divide × fH` が狙いのDATACLKになるか**で見る
(実測 1820 × 15699 = 28.572 MHz = 8fsc)。`status` はこれを出す。

**見え方の期待値**

- **グレースケールの細長い絵になる**(`pixfmt=YC8` なので Viewer は緑ch=CVBSを
  そのまま輝度に置く)。横は 1820 サンプルぶん
- ラインの左端に **同期チップ→ブリーズウェイ→カラーバースト→バックポーチ** が
  帯として見える。ここが見えていればブランキング区間ごと届いている
- 色のある部分に**副搬送波由来のチェッカー/ドットクロールが出る**。これが「復調前の
  クロマがちゃんとサンプルされている」証拠になる

**ここで止まったら**: PLLがロックしないときは 0x19 のチャージポンプを 1/2/3 で振る。
同期が取れないときは 0x50(SOG閾値、既定0x0B=124mV)と 0x5D(SOG LPF を 01=10MHz へ)を振る。
`status` が指摘として出す。

### Step 2 — レベルを実測で追い込む ← **配線ができたらここ**

**絵が出ても終わりではない。** §2 のとおり、失敗は「絵は出ているのに復調できない」
形で出る。数値で判定する:

    python3 -m retrocastx.videoin --board <ボードIP> probe

出力は同期チップ・ブランキング・バースト p-p・映像 min..max を**コードとIREの両方**で
出す。IREへの換算は「同期チップからブランキングまでが 40 IRE」を使うので、
**絵の内容に依存しない**(ただし両端のどちらかが飽和していると校正そのものが
崩れるので、そのときはIRE行を出さない)。

さらにラインの先頭を縦棒グラフで描く。列ごとに **min..max を塗る**ので、8fscの
バースト(1周期8サンプル)が**帯の太さ**として残る。合成波形での見え方:

```
127 |                               ###############################          ← ブランキング
109 |                                   # ######## # ###                     ← バーストの下側
 91 |###############################                                         ← 同期チップ
    +------------------------------------------------------------------------
                                   S   b                B         P
```

飽和すると上端/下端に張り付いた線になるので、数字を読む前に形で分かる。

合格の目安:

| 量 | 期待値 | 外れたときに振るキー |
|---|---|---|
| ブランキング | 128付近(ミッドレベル) | 0x5E(クランプ選択) |
| 同期チップ | 0に張り付いていない | 0x5E / 0x5F |
| 映像 max | 255に張り付いていない | **0x5F(粗ゲインを下げる)** |
| バースト p-p | 36コード前後(下限24) | 0x5E / 0x5F / 0x65 |
| バースト周期 | 8.00 サンプル/周期 | 0x12(pll_divide) |

判定ロジックの回帰試験は `host/python/retrocastx/tests/test_videoin.py`
(合成したNTSC 1ラインで、正常系・ボトムレベル・ゲイン過大・クランプ位置ずれの
4通りを区別できることを確認している)。

### Step 3 — 8bit で送る(実装済み)

RGB555 では 3bit 捨てるので復調に足りない:

```
5bit (32コード)  → 4.4 IRE/コード  → バースト  4〜5段階   ← 位相推定が成立しない
8bit (256コード) → 0.55 IRE/コード → バースト 36コード p-p ← 実用十分
```

(当初「8bitならバースト73コード」と書いていたが、それは140 IRE を256コードに
フルに割り当てた場合。ミッドレベルクランプのヘッドルーム分を引くと36が上限。§2参照)

**採った実装は `pixfmt=3 (YC8)`。** 2B/px のまま「下位バイト=緑ch8bit /
上位バイト=赤ch8bit」にする。

- **1B/px の専用形式は要らなかった。** 2B/px なら断片化・MTU計算・受信側の
  バッファ確保が RGB555 とまったく同じで済む(帯域は 466 Mbps。GbEの半分弱)
- **S-Video にそのまま乗る。** Y8+C8 = 16bit なので、1番系統を実装したら
  上位バイトが C になるだけでプロトコルは変わらない

★**黒トリム最適化は YC8 では自動的に切れる。** コンポジットは**バーストも含めて
ライン全体が中身**なので範囲の概念が成立しない。設定漏れで壊れるより形式から
決まる方が事故が少ないので、`cfg_pixfmt == YC8` のとき `cfg_full_line` 相当を
強制している(`retrocastx_stream.py` の `send_full`)。

### Step 4 — デコーダ(参照実装は動いた。Viewerへの移植が残り)

`host/python/retrocastx/ntsc.py` が参照実装。実機のPS2起動画面で復調できた:

```
バーストが取れた行 253/263   隣接ラインの位相差 177.8°
既知の色との誤差    ○決定=赤 -1.0° / グロー=シアン +14.0°
                    ブラウザ=青 -18.9° / △本体設定=緑 +25.5°   (色相補正 0°)
```

**色相の合わせ込み係数は入れていない**(`--hue` の既定は0)。バーストが
-(B-Y)軸という規格の定義だけから正しい色が出る。

△だけ +25.5° 残る理由は**未確定**。当初「2次元コムが小さく孤立した図形で崩れる
ため」と考えて2次元適応コムを書いたが、**実測では △ の誤差が変わらなかった**
(25.5° → 25.9°)ので、その仮説は否定された。

いま有力なのは **期待値の120°の方が推測だった**という説。PS2の△の緑が本当に
色相120°かは確かめていない(○=赤の0°は安全な仮定で、そちらは -1.0° に収まる)。
確定させるにはカラーバーのように**色相が規定されている映像源**が要る。

なお図形の外側の低彩度の行では色相が乱数のようになる(彩度0.03〜0.09で
色相が230〜300°をふらつく)。これは真っ黒な領域で相関が雑音になるためで、
Viewer側はバーストの相関が下限を割った行を無彩色に倒している。

    python3 -m retrocastx.videoin --board 255.255.255.255 capture --out cvbs.npz
    python3 -m retrocastx.ntsc --in cvbs.npz --out out.png [--hue N] [--sat N]

★**V(R-Y)軸の符号は実測で決めた。** 最初は逆に書いていて、既知の2色が
どう色相を回しても同時に合わなかった(2色の開きが149.8°、本来240°)。
回転は点の間の関係を変えないので、**1色だけで合わせていたら「オフセットが要る」
で片付いて気づけなかった**。詳細は design-notes.md。

#### Viewer(Rust)にも入れた — `client/src/ntsc.rs`

構成:

    C = 3次元(動き適応フレームコム)。静止部分は1 NTSCフレーム前と引く
        動いている所は2次元(ラインコム)へ落とす
    Y = x - Ĉ    帯域制限した U,V を再変調して引いた残り
    動き検出 = 2 NTSCフレーム前との輝度差(位相0°なのでクロマが混ざらない)
    フレームコムの前に、1フレーム前との副搬送波位相のズレ ε を戻す(下記)

#### フレームごとに入れ替わる縞(ドットクロール)の原因と対処

実機で「一見フラットなオレンジ帯が、スクショだと赤黒赤黒に見え、**フレームごとに
黒赤黒赤へ入れ替わる**」という症状が出た。切り分けの記録:

まず**同一データ**で構成を比べ、実装に固有の欠陥ではないことを確かめた
(静止・平坦・彩度38.4 IREの画素で、輝度に残る副搬送波の中央値):

    元信号 X                    38.41 IRE
    (X+P2)/2 = 理想的なフレームコム  1.58 IRE
    X - Ĉ  (実装)                1.57 IRE   ← 理想と同じ。帯域制限は無罪

つまり残留は**フレームコムがそもそも消しきれない量**。原因は
**DATACLK が HSYNC にロックしていて副搬送波にはロックしていない**こと。
フレームをまたぐと副搬送波とサンプル格子の位相関係が歩く:

    ε(1フレーム前との位相ズレ)  |中央値| 4.80°  行方向に滑らかに±15°を揺れる

残留は C·sin(ε/2) なので 38.41 × sin(2.40°) = 1.57 IRE。**実測の 1.57 IRE と
一致した**(独立な2通りの測り方が同じ値を出した)。副搬送波成分なので
1フレーム(=2フィールド)で符号が反転する = 見えている入れ替わり。

対処は c3 の位相を ε/2 戻すこと。**8fsc では2サンプル遅延がちょうど90°**なので、
ヒルベルト変換を持ち出さずに1サンプルあたり積和1回で書ける:

    c3(n) - c3(n-2)·tan(ε/2)

実測(同じ静止・平坦・彩度の高い画素): 1.57 → **1.20 IRE**。符号を逆にすると
2.38 IRE に悪化するので、効いているのは偶然ではない。画面全体で見てもどの
パーセンタイルも悪化しない(中央値 0.98→0.90、90%点 5.32→4.99 コード)。

**ここが底。** 信号の無い区間(バックポーチ)の fsc ノイズ床が 1.45 IRE
(2フレーム平均で 0.90)なので、補正後の 1.20 IRE は既にノイズ床。
残りは基板側のアナログノイズ(バックポーチのライン間 σ 3.42 IRE = ハム)。

隣接ラインどうしのズレは 2.19° と小さく、**2次元コム側は直しても効かない**
(1.34 → 1.29 IRE)。フレーム間隔16.7msでドリフトが溜まるので筋が通る。

なお NTSC は 1フィールド = 262.5ライン × 227.5周期 = 端数0.75周期なので、
**副搬送波の位相はフィールドごとに270°(=−90°)回り、4フィールドで一巡する**。
ただし我々の行番号は半ライン単位のスロットで、フィールド間に半ライン(270°)の
オフセットが入るため、**スロット基準では 0°/180° の交互**に見える。実測:

    同じスロット 2フィールド後 (=1 NTSCフレーム)  +166.3°  → 180°
    同じスロット 4フィールド後                     +0.4°   → 0°

つまり縞が完全に元へ戻る周期は4フィールド、符号が反転する周期は2フィールド。
どちらも上の ε とは別の話で、ε はこの 180° を引いた**残り**を指す。

`--dump-frame ... --dump-seq N` で連続フレームを落とせる。「1枚では分からない
現象」はこれで追う(この症状の切り分けに実際に要った)。

★**Yをコムやノッチから作ってはいけない。** どちらも1本の線を3本に広げる:

    Y の作り方        縦線への水平応答     横棒への垂直応答
    x - C_comb        100% の1本  ○       25%/50%/25%  ×
    x - C_notch       25%/50%/25% ×       100% の1本   ○
    x - Ĉ (これ)      100% の1本  ○       100% の1本   ○

実機で「漢字の横棒が二重」→(ノッチに変更)→「鼻の縦線が二重」と、**artefactを
垂直から水平へ付け替えただけ**の失敗を2回した。回帰試験は必ず両方向を見る。

以下は当初の「Yはノッチ / Cはコム」の記録(いまは上の再変調に置き換えた):

    C = (x - (up + dn)/2) / 2        コム。上下は互いに同位相なので輝度が消える
    Y = (2x + x[n-4] + x[n+4]) / 4   ノッチ。8fscでは4サンプル=副搬送波の半周期
    U,V = 直交復調(バースト位相基準) → 16タップ移動平均 → YUV→RGB

**輝度をコムから作ってはいけない。** コムのYは垂直方向のLPFで、1本の横棒への
応答が 25%/50%/25% に広がる(実機で漢字の横棒が二重に見えた)。ノッチなら
100%の1本。実測で**垂直解像度が3.2倍**になった。
**クロマはコムのまま**(ノッチのクロマは輝度の漏れ込みが多い)。


実機での結果(headless、PS2起動画面):

```
NTSC復調: 253行ロック  コム間隔2  位相差178°(180°が正常)
2048x526  60.0 fps  468.9 Mbps  frames=451 lost=0 qdrop=0 orphan=0
```

**負荷は1コアの 11.9%**(Apple M4 Pro、シングルスレッド、release)。
1フィールド 1.989 ms、240.7 MSa/s 相当。60フィールド/秒を回しながら
パケットロス0を維持できている。測り方は
`cargo test --release -- --ignored --nocapture ntsc::tests::timing`。

軽い理由は 8fsc であること。`cos(2πn/8)` は `n mod 8` の8点しか取らないので、
位相基準がライン毎のバーストから決まれば**1サンプルあたり積和2回**で復調できる。

★**コムのペアは決め打ちにせず測って決める。** フレームバッファの行番号は
「フィールド内の行×2 + 極性」なので、1フィールドだけ来ている間は**奇数行だけ**が
埋まり、時間的に隣なのは N と N±2 になる。織り込み設定でも変わる。
行差1と2の両方で位相差を測り**180°に近い方を採る**(実機は間隔2を選んだ)。
決め打ちだと設定が変わった瞬間に色が消える(同位相の行を引いてクロマが0になる)。

復調がロックしないとき(バーストが無い信号、モノクロ、同期だけ)は fb を触らず、
ライン受信時に書いたYのグレースケールが残る。波形の確認がそのままできる。

#### 残り: 画質

- **色相の絶対確認にはカラーバーが要る。** いま合わせられているのは ○=赤 の
  0°(誤差 -1.0°)だけで、他3つの期待値は写真からの目視。△の +25.5° が
  デコーダの誤差なのか期待値の推測ミスなのか、この素材では決められない
- **2次元適応コムは実測で悪化した(既定オフ)。** 白文字の偽色が 0.0260 → 0.0428。
  ノッチ自体は正しい(合成6色で2次元コムと同じ誤差2.1°)が、細い縦棒の輝度が
  副搬送波の近くにあるため、垂直detailで切り替えると**より悪い方へ行く**。
  まともにやるには「垂直detailが大きく**かつ**水平fscエネルギーが小さい」条件が
  必要。本筋は時間方向を見る**3Dコム**で、それはGPU向き(下記)
- **ドットクロールはノイズ床まで落ちた。復調側にもう伸びしろは無い。**
  次に効くのは基板側だが、**高域は落ちていない**(下記)。残るのはノイズで、
  バックポーチのライン間 σ が 3.42 IRE(ライン内は 1.66)。低い周波数の
  ハム/グラウンドが乗っている。ここが直ると ε の測定精度も上がる

#### 水平解像度の上限は**入力側**にある(2026-08-15 実測)

実機で「鼻の縦線が二重」「襟のラインがダブる」が残っていたので測った。
細い線と影がにじんで融合すると二重に見える。

★**まず自分の測定を疑うこと。** 当初「バースト振幅 7.3コード / 期待17コードで
  2.3倍減衰。手半田で高域が落ちている」と結論しかけたが、**これは誤りだった**。
  相関から出るのは振幅で、p-p はその2倍。数え直すと:

    バースト  31.6 IRE p-p(生の最大-最小で 35.2)  規格 40 IRE p-p
              → 0.79倍 = **-2.1 dB だけ**。単極とみて fc = 4.6 MHz
    同期の立ち上がり 154 ns(規格 140 ns)
              → 経路が足した鈍りは √(154²-140²) = 64 ns = **5.5 MHz**

  2通りとも「経路は 5MHz 前後あって問題ない」で一致する。基板は無罪。

一方、絵のエッジはそれよりずっと遅い(フレームコム輝度 (x+p2)/2 で測定。
水平方向のフィルタを一切通していない):

    立ち上がり時間  5%点 174 ns (2.01 MHz)   50%点 195 ns (1.79 MHz)
    輝度スペクトル  2.0MHz -13.2 dB → 3.0MHz -24.9 dB
                   (0.58オクターブで 11.7 dB ≒ 3次のフィルタ)

**分布に下限がある**のが決め手。絵の内容のばらつきなら、もっと速いエッジも
混ざるはず。下限が 174 ns で揃い、しかも 2→3MHz の落ち方が急なので、これは
設計されたフィルタ。経路が 5.5MHz ある以上、**上流(コンポジット出力側)の
輝度ローパス**しかない。コンポジットは 3.58MHz にクロマが載るので、
クロスカラーを避けるために輝度を 2MHz あたりで切る機器は珍しくない。

つまり**この鈍りはコンポジットである限り取り返せない**。輪郭補正で持ち上げる
ことはできるが、エッジの両側に行き過ぎが出て「線が二重」の見え方はむしろ悪化する
(過去にノッチで同じ失敗をしている)。

→ **S端子で確かめ、そのとおりだった(2026-08-15)。**

#### 決着: PS2のコンポジット出力そのものだった

オシロ(Rigol MSO1074Z、Videoトリガでライン指定)で **AC結合コンデンサより手前**、
つまりこちらの回路の外で PS2 の出力を直接見てもらった:

    コンポジット  細い罫線の谷が浅く、**谷底に段がある**
    S端子の Y     同じラインが単一の深い谷。立ち上がりもほぼ垂直

こちらの収録と数値も一致した(ブランキング161 = 0 IRE、1 IRE = 0.825コード):

    白地            103 IRE
    太い罫線の谷底   50 IRE   ← オシロで約1.8div(200mV/div)
    細い罫線の谷底   68 IRE   ← 約1.1div
    谷底の持ち上がり 82 IRE   ← 谷の深さの38%

★**太い罫線ですら谷底が 50 IRE までしか落ちていない。** 黒は 0 IRE なので、
  PS2 のコンポジット出力の時点で細い線は半分しか沈んでいない。

これで送出側のどこかも確定した。**コンポジットのエンコーダの輝度処理**であって
本体のスケーラではない(スケーラなら S端子の Y にも出るはず)。

#### だから S端子ではコムが丸ごと要らない

    項目            コンポジット              S端子
    Y               x - Ĉ(コムで色を抜く)   **そのまま**
    C               3次元コム+動き適応+ε補正  **赤chを直交復調するだけ**
    クロスカラー     原理的に残る              **原理的に無い**
    ドットクロール   ε で残る(ノイズ床まで)   **原理的に無い**
    輝度帯域        送出側が2MHzで切る        切る理由が無い

実装済み(`ntsc.py` / `ntsc.rs` 両方、2026-08-15):

- ★**どちらの方式かは測って決める。** 赤chのバースト区間と、同じチャネルの
  バックポーチ(信号なし)の fsc 相関の比を見る。絶対値で閾値を切るとチャネルの
  ゲイン設定に依存するので比にした。実測: コンポジット収録で **緑ch 54.5 /
  赤ch 1.09**(判定の下限は6.0)。50倍の開きがある。選択に頼らないので、
  配線と Viewer の設定が食い違っても絵が出る
- クロマのスケールは**バースト基準**にする。赤chはクランプもゲインも緑chと別
  設定なので Y の code_per_ire は使えない。バーストは規格で 40 IRE p-p なので
  それをものさしにすると、チャネル間のゲイン差が自動的に打ち消える
- 回帰試験は両方に置いた(色相6色 / 判定の正負の対照 / C側ゲイン半分でも同じ絵 /
  輝度が素通し)。負の対照は実データでも確認済み(コンポジット収録で
  `svideo=False`、絵は c_rows を渡さない場合と1コードも変わらない)

配線は **Y→Gin3 / C→Rin3 / SOGin3 は Y から分岐**。Viewer の「映像ソース →
S端子」でレジスタは入る。配線後に `videoin probe --mode svideo` で
Y/C それぞれの飽和とバースト振幅を見て粗ゲインを詰めること(role ごとに
期待値が違う。Yは同期チップが飽和しているのが正常、Cはブランキングが128付近)。
- GPUへのオフロードも可能(下記)

#### GPUへ移す余地

いまはCPU。1コアの12%なので急ぐ必要は無いが、移せる構造にはなっている:

- 復調は**サンプルごとに独立**で、コムが上下1本を見るだけの局所演算。
  フラグメントシェーダの得意な形
- **転送量はむしろ減る。** 生サンプルは 1820×526×2 = 1.9MB/フィールドだが、
  いまGPUへ送っているRGBAは 1820×526×4 = 3.8MB。**生を送って
  シェーダで復調する方が転送は半分**
- ライン毎のバースト位相だけはCPUで出す方が素直(66サンプル×262行 = 17k
  サンプルで全体の0.06%。GPUでライン単位の縮約をやる手間に見合わない)。
  位相の cos/sin を 1×N のテクスチャで渡す

### 当初の Step 4 の構想(参考)

**FPGAではなく Viewer 側でやる。** 理由:

1. **帯域は生を送る方が少ない。** コンポジットは1チャンネル、デコード後は3チャンネル
   ```
   生 1ch 8bit @28.6MSa/s                   = 229 Mbps
   FPGAでデコードしてRGB555 (720×480@60)     = 332 Mbps
   ```
2. **画質の天井が高い。** 良いコムフィルタは動き適応の2D/3D(ライン間だけでなく
   フレーム間も比較)で、フレームバッファを何枚も要る。ソフトなら自然、
   ECP5-25 で外部メモリ帯域を割くのは厳しい
3. **開発の回転が速い。** キャプチャを一度録ればオフラインで何通りも試せる。
   FPGAはビットストリーム再生成とタイミングクロージャが毎回付く
   (`eth_rx` が 123.59MHz で FAIL した経緯がある。`--timing-allow-fail` で
   通ってしまうので**post-route のレポートを見ること**)
4. **プロジェクトの思想に合う。** FPGAは実時間を測って生を送り、Viewerが再構成する

**やること**

- ライン毎に**バーストへ位相ロック**する(ライン番号のパリティから予測するより堅牢。
  RetroCastX が「ドット数・ライン数に頼らず実時間で位置を決める」方針なのと整合する)
- 8fsc なら副搬送波1周期あたり8サンプルなので、直交復調は加減算主体で書ける
- Y/C分離はまずライン単位の2次元コム(隣接ラインとの加減算)。NTSC は 227.5周期/ラインで
  バースト位相が1ラインごとに180°反転するので、加算でY・減算でCが出る
- 余裕が出たら動き適応の3次元コムへ

## 6. 落とし穴

| 落とし穴 | 対処 |
|---|---|
| **ミッドレベルクランプだけ入れると白が飽和する** | 粗ゲイン(0x5F)を 0x07 まで下げる。§2 |
| バーストの上でクランプすると基準がずれる | クランプ開始を 230前後(バースト後)に |
| ボトムレベルクランプではバーストの下半分が消える | 0x5E=0b010、または 0x65 でブランキングを持ち上げる |
| RGB555 のままでは復調精度が足りない | 0x36=3(YC8) |
| **「絵が出た」では合否が判定できない** | `composite probe` で数値を見る |
| PAL 8fsc(2270)はキャプチャバッファ2048に入らない | 4fsc(1135)か バッファ拡張 |
| ミッドレベルクランプ・粗ゲインをRGB入力に残すと絵が壊れる | `composite restore` で戻す |
| 黒トリム最適化が効かず全ライン送ることになる | YC8では自動で全ライン(帯域 466 Mbps) |
| SOG閾値を上げ過ぎるとバーストで誤トリガ | 既定の2.5MHz SOG LPF を維持 |
| **ロジックを足すと `eth_rx` が 125MHz を割る** | `--seed` を振る。原因はLiteEthのMAC tx CDC FIFOの配置運で、こちらのロジック量とは無関係(2026-08-14 の実測: 配線 6.17ns / 論理 1.94ns) |

## 7. 将来: S-Video 化(基板発注前に部品だけ置いておく)

コンポジットの一番難しい部分(Y/C分離)は、**S-Video なら丸ごと消える**。
1番系統(`rin_1`/`gin_1`/`sogin_1`、現在すべて未使用終端)が空いているので、
PCB を起こす前に R/C だけ置いておけば後から対応できる。

**既存の3つのシュントコンデンサが既に正しい位置にある**(TVPピン直近)。
値を 33pF に変えればアンチエイリアスとしてそのまま使える。

```
nc_caps[0]      rin_1   → GND   10nF → 33pF   C(色差)チャンネルのAA
nc_caps[2]      gin_1   → GND   10nF → 33pF   Y のAA
nc_sog_caps[0]  sogin_1 → GND    1nF → 33pF   SOG分岐のAA
```

**追加は 0402 が9個 + 1×4ヘッダ + ESD 1個**。定数は既存RGBチャンネルと同一。

```
1×4ヘッダ ──┬── Y  ─┬─ 75Ω ─ GND
             │       ├─ 100nF ─ 220Ω ─ GIN_1    (+既存33pF)
             │       └─ 100nF ─ 220Ω ─ SOGIN_1  (+既存33pF)
             ├── GND
             ├── C  ─┬─ 75Ω ─ GND
             │       └─ 100nF ─ 220Ω ─ RIN_1    (+既存33pF)
             └── GND
```

- ヘッダにしておけば**コネクタを今決めなくて済む**。後からピグテールでRCAでも
  mini-DIN でも付けられる
- **DNPにせず最初から実装してよい。** 75Ωが入力ノードをDC的にGNDへ落とすので、
  信号が来ていなくても未使用入力として静か(データシートが10nFを求める理由は
  「浮かせない」ことなので、これで満たせる)
- **S-Video なら C チャンネルが8bitを丸ごと使える。** チャンネルごとに独立した
  ゲインとクランプを持つので、クロマ振幅(±60 IRE程度)に合わせてゲインを上げられる。
  コンポジット(140 IRE を輝度と分け合う)に比べてクロマ分解能が約4倍
- mini-DIN 4 は Y ピンにコンポジットを流す変換ケーブルが安く手に入るので、
  コネクタ1個で S-Video とコンポジットの両方をカバーできる
