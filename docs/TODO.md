## 1. 受信パケットからARPテーブルを学習させる(案B)

Windows で「ボードが送れない」問題の本筋の対策。詳しい経緯は
[design-notes.md](design-notes.md) の「実機を動かすときの準備」を参照。

**問題**: ボードは返信のために相手のMACをARPで引くが、**Windows は別サブネットの
送信元から来たARP要求に応答しない**(strong host model)。macOS/BSD は応答するので
macOS だけの検証では見落とす。さらにボードのARPキャッシュは**2エントリしかない**
(`arp_entries=1` → `max(entries,2)`)ので、3つ以上のIPが関わると追い出しが起き、
一度追い出されると Windows では復帰しない。

**当座の回避(いま実機はこれで動いている)**: Windows 側にボードと同じサブネットの
アドレスを足す。`New-NetIPAddress -InterfaceAlias 'イーサネット' -IPAddress
192.168.10.35 -PrefixLength 24`(Windows は永続化する)。

**やること**:
- 受信パケットの「イーサネット送信元MAC + IPヘッダの送信元IP」を
  `arp_table.update`(`ip_address` + `mac_address` を持つ既存のエンドポイント)へ流す
- LiteEth 本体は触らず、`retrocastx_stream.py` で `ethphy` と `ethcore` の間に
  タップを挿すのが筋。IP層はイーサネットの送信元MACをUDP層まで運ばないので、
  MAC層のRXを分岐させて自前でIPヘッダを覗く必要がある
- あわせて `arp_entries` を 1 → 8 程度に増やす(こちらから先に送る相手のために必要)

**効果**: SUBSCRIBE を受けた瞬間に相手のMACが分かるのでARPの往復が不要になり、
相手がARPに応答しない環境でも動く。利用者に New-NetIPAddress を要求しなくなる。

## 2. 受信スレッドが 27000パケット/秒を捌けない(低スペック機)

マルチスレッド化(受信専用スレッド + 組立スレッド)を入れた後の残り。
Windows の低スペック機で 260Mbps / 55fps のとき:

    lost 114985 / 2055863 = 5.6%   OSのUDPバッファ溢れ
    queue drops 0                   組立側は追いついている
    paint 55.49Hz                   描画も追いついている

**`queue drops` が0なので、詰まっているのは受信スレッド単体**。`recv_from` だけを
回しても 27000回/秒に届いていない(syscallのコスト限界と見ている。未測定)。

`間引き 1`(2フレームに1回)にすると音の途切れは無くなる。実用上はこれで凌げる。

**候補**:
- 受信スレッドを複数にする。ただしパケットの順序が乱れ、`track_seq` の lost 集計が
  壊れる。フレーム境界の判定(`l.frame != cur` で emit)も乱れる恐れがあり要注意
- キュー操作をまとめる(いま1パケットにつきチャネル操作が3回ある)。ただし
  支配的なのは `recv_from` 自体と見られるので効果は限定的
- ジャンボフレームで1パケットに複数ラインを詰める。パケット数が数分の1になるが、
  プロトコルとゲートウェアとスイッチの対応が必要
- まず**CPU使用率を測って本当にsyscall律速か確かめる**のが先

## 3. lost / orphan lines の追跡

長時間動かすと `lost` が少しずつ増える(13469フレームで19072パケット ≒ 0.08%)。
`orphan lines`(MODEの mode_id が一致しないLINEを捨てた数)も増える。モード切替を
繰り返したセッションで増えただけなのか、定常状態でも増えるのかを切り分ける。

## 4. ライン長を超える断片が0.5%

各フィールドの特定位置(413行目付近と879行目付近)に集中する。HSYNCを取り逃がした行で
`x` が長く走り、非黒範囲がライン長を超えると考えている。受信側は入る分だけ書いて
凌いでいるが、ボード側で範囲をライン長で打ち切るのが本筋。

## 5. 管面の縦横比がCPU側とシェーダ側で食い違う

`tube_aspect = 0`(管面「そのまま」= 既定)のとき、両者が別の値を使う:

- CPU側(`main.rs` の CentralPanel): 切り出し範囲の比 `cw/ch`
- シェーダ側(`render.rs` の `uniforms`): 時間ベースかつ幾何が有効なら **4:3 固定**

描画callbackの矩形はCPU側の比で確保されるので、実際に映る管面はその中で
レターボックス/ピラーボックスされる。`画に合わせる` はCPU側の比でウィンドウを
決めるため、押しても管面はぴったり収まらない。

外側の色を撤去して黒に統一したので見た目には出ないが、比の計算が2か所にあること
自体が原因。本筋はシェーダに `avail` 全体を渡して管面の形をシェーダだけに決めさせ、
`画に合わせる` 用に描画サイズを返してもらうこと。

## 6. モニタプロファイル

`mon.15` / `mon.24` / `mon.31` に [H幅, H位置, V幅, V位置] を持つ。実CRTのつまみに
相当し、スライダーで合わせる。将来は CZ-600D / CZ-612D のような実在モニタの
プロファイルを外部ファイルにする案がある(オーバースキャン量、走査線の強さなど)。

信号は左右非対称(バックポーチが長い)なので `H位置 0` だと絵が右に寄る。
実測例: 15kHz Mode7 は `active 994x480 at (157,33)`, htotal 1179 → 適正な H位置は
(157 + 994/2)/1179 - 0.5 = +0.055。

## 8. pll_divide の自動決定(部分的に完了)

`自動調整` ボタン(Viewer)と `pll_tune autotune`(CLI)がある。上限まで過剰サンプルして
スペクトル占有率から倍率を割り出し、8の倍数で±7%だけ局所探索する。24kHzで真値1408に
着地することを確認済み。

**映像ソースのプロファイル方式を追加した**(Viewerの `映像ソース` プルダウン)。fH と
ドットクロック候補から htotal を決めるので、絵の内容を一切見ない。X68000 の3帯域で
正解する(回帰テストあり)。原理と選び方の落とし穴は design-notes.md 参照。

未対応:
- VGA / PC-9801 のプロファイルは数値の裏を取っていない(実機で確認が必要)
- スペクトル探索の `自動調整` は残してある。プロファイルで pll_divide を決めてから
  位相だけを振る形に整理するとよい
- 誤った状態(PLLが外れている、絵が真っ暗など)から始めると失敗する。開始前に
  健全性を確認する仕組みが無い
- TVPのピクセルクロック下限(12MHz)により1:1にできないモードがある(15kHz 512x512 は
  本来の htotal 608 = 9.72MHz なので2倍の1216を使う)。下限を満たす最小の整数倍を
  選ぶ処理は入っているが、実機での検証は24kHzのみ

## 参考: 現在の設計の要点

**幾何は同期信号だけで決まり、絵の内容に依存しない。**

```
水平位置 = (offset_px + k) / htotal      offset_px はライン内の絶対位置
垂直位置 = スロット / (slot_k × vtotal)   slot_k は mflags bit0 で伝える
```

**インターレースは設定ではなく測定で決まる。**

```
TVPの検出ビット(38h bit5)      インターレースかどうか
生VSYNCの半ライン位相          どちらのフィールドが下か(次のHSYNCまでが短い側が上)
TVP vtotal / 生ライン数の比    フィールド単位かフレーム単位か
```

**生同期(P4 pin155=HSYNC / pin153=VSYNC)は sysドメインで測る。** pll_divide に依存
しない絶対値が得られる(key 0x2A/0x2B/0x2C)。TVPのHSOUT/VSOUT経由の値は、TVPが
インターレースのVSYNCを間引くのでフレーム単位に畳まれている。

**pll_divide はドットクロック再生専用で、描画位置に影響しない。** hs_offset は
設定項目から撤去済み(既定0)。
