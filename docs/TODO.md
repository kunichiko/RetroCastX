### 入力方式の切り替えは全部CONFIGで済むようになった

手組みボードの配線(排他)と、それぞれのレジスタ:

| モード | 映像 | 同期 | reg 19h | reg 0Eh |
|---|---|---|---|---|
| `x68k` | Rin3/Gin3/Bin3 | HSYNC_A / VSYNC_A | 0xAA | 0x52 |
| `msx` | Rin3/Gin3/Bin3 | **SOGin2** (CSYNC) | **0x6A** | 0x5B |
| `composite` | Gin3 (CVBS) | SOGin3 | 0xAA | 0x5B |
| `svideo` | Gin3=Y / Rin3=C | SOGin3 | 0xAA | 0x5B |

★**msx だけ SOG の入力ピンが違う**。レジスタ19h はビルド時定数だったので、
以前は**焼き直さないと MSX に切り替えられなかった**。key 0x69 で解決。

`videoin auto` が自動判別する。3方式は**同期がどこに来るかが違う**ので絵を見ずに
判別できる。最初の分岐に使う生HSYNC(key 0x2A)は TVP を通らない経路を sys ドメインで
数えた絶対値なので、TVPの設定に依存せず読める。
`composite`/`svideo` は同期の出方が同じなので `auto --svideo` で指定する。

### 入れたもの

- CONFIGキー **0x36**(pixfmt)/ **0x5E**(クランプ選択 reg10h[2:0])/
  **0x5F**(粗ゲイン reg1Bh=B/G)/ **0x65**(粗オフセット reg1Fh=G)/
  **0x67**(粗ゲイン reg1Ch=**R**)/ **0x68**(粗オフセット reg20h=R)/
  **0x69**(入力MUX reg19h)
- **pixfmt 3 = YC8**(2B/px、下位=緑ch8bit=CVBS/Y、上位=赤ch8bit=S端子のC)。
  2B/pxのままなので断片化もMTU計算も既存と同一。ViewerはYをグレースケールで出す
- `retrocastx.videoin` — 方式の一括切替・自動判別・**波形の実測判定**

★**1Bh と 1Ch はビット割りが違う**(1Bh=`[7:4]G [3:0]B` / 1Ch=`[7:4]予約 [3:0]R`)。
同じ1.2倍でも 0x77 と 0x07。S端子のCは赤chなので 1Ch が要る。

### S端子は既存のD-SUB経路で試せる

計画書 §7 の「1番系統に部品を足す」は**専用コネクタを付けるための話**で、前提条件では
ない。R/G/Bは同一の前段(75Ω+100nF+220Ω/33pF)なので、**Y→緑 / C→赤**で今日試せる。
Yを緑に入れるのは固定(SOGタップが緑にしか無い)。
YとCで独立にクランプとゲインを持てるぶん、輝度もクロマも**約2.4倍**の分解能になり、
なにより**Y/C分離が丸ごと不要**になる(Step 4 の一番難しい部分が消える)。

### 当初の計画から変わった点(重要)

- **ミッドレベルクランプ単独では成立しない。粗ゲインを同時に下げる。**
  ブランキングが512に座るので白側ヘッドルームが半分になり、既定の1.2倍のままでは
  コンポジット(1Vpp=140IRE)が飽和する。`1Bh = 0x07`(0.5倍)が出発点
- **バーストは73コードにはならない。36コードが上限**(ヘッドルーム半減のぶん)。
  それでもRGB555の4〜5段階よりは4倍以上良い
- ボトムレベルクランプでもブランキングは0ではなく**約64**(粗オフセット1Fhの既定)
- **粗オフセット(1Fh)でブランキングを動かす別解は成立しない。** 粗クランプは
  既定で無効(reg 2Dh)で、ファインクランプの帰還ループがADC前のオフセットを
  打ち消す。実測で +64→+0→-32 と振ってもブランキングが動かなかった。
  白の飽和に効いたのは**ファインゲイン(09h)**(33=1.129倍が掛かっていた)
- **「絵が出た」では合否が判定できない。** ボトムレベルならバーストの下半分が消え、
  ゲイン過大なら白が飽和する。どちらも絵は出る。だから `probe` で数値を見る

### Y/C分離は 3次元(動き適応フレームコム)まで実装した

    1次元  水平のみ(BPF/トラップ)          メモリ不要
    2次元  + 垂直(ラインコム)               1H
    3次元  + 時間(フレームコム、動き適応)  1フレーム  ← いまここ

★用語注意: 英語圏の "1H comb / 1D comb" は上下ラインを使うものを指すが、
**日本語の「1次元」は水平のみ**を指す。当初この文書は英語の言い方で
「1Dコム」と書いていたので、日本語の2次元/3次元に統一した。

**成立の根拠(実測)。** NTSCは1フレームあたり 525×227.5 = 119437.5周期で
端数0.5周期なので、1フレームで位相が180°反転する。ボードの「フレーム」は
1フィールドなので同じライン番号は2フレームおきに来る:

| ボードのフレーム差 | NTSCフレーム差 | 位相差(n=4576) | 用途 |
|---|---|---|---|
| 2 | 1 | **175.8°** | フレームコム(C を取る) |
| 4 | 2 | **4.2°** | **動き検出**(クロマが混ざらない) |

★**動き検出に1フレーム前を使ってはいけない。** 位相180°なのでクロマが差に
そのまま出て、色のある所が全部「動いている」ことになる(映像域の副搬送波成分で
9315 対 388)。2フレーム前なら位相が同じなのでクロマが消え、純粋な輝度の時間差になる。

**効果(同じフレームを両方式で復調、15フレーム平均)**:

| | 2次元 | 3次元 | |
|---|---|---|---|
| 垂直detail上位10%の彩度(偽色) | 0.1523 | **0.1447** | −0.0076 |
| 平坦部の彩度のσ(ノイズ) | 0.2583 | **0.2477** | −0.0106 |

静止部分ではフレームコムが厳密解なので、フレーム差を取っても**クロマはむしろ
綺麗になる**(ノイズが増えるという当初の懸念は外れた)。

負荷は 1コアの 15.4% → **19.6%**(M4 Pro、シングルスレッド、release)。
メモリは履歴2面ぶん +3.8MB。

実機: 263行すべてが3次元、動きと判定されたのは 1.4〜2.4%、lost 0。

### 残っているのは GPU化 ← **次のセッションの主題**

CPU実装は 2次元/3次元コム・位相ドリフト補正・S端子まで揃っていて、実機で
安定して動いている。次は GPU オフロード。

#### なぜやるか(動機が1つ増えた)

1. **CPU負荷**: 1フィールド 3.85ms = 1コアの23%(`cargo test --release --
   --ignored --nocapture ntsc::tests::timing` で測れる)
2. **転送量**: 生サンプルを送る方が半分(1.9MB/フィールド 対 いまのRGBA 3.8MB)
3. ★**publish の揺らぎが減る**(2026-08-15に判明)。表示できる新フレームの割合は
   **到着の揺らぎ σ で決まり**、その σ = 4.35ms は復調時間 3.85ms とほぼ同じ。
   publish のタイミングが処理時間のばらつきを引き継いでいる。
   **復調を軽くするのは、見に行く回数を上げるのと同じ効果を持つ。**
   根拠と確率モデルは [design-notes.md](design-notes.md)「表示レートは
   『見に行く回数』で決まる」

#### 進め方(順序に理由がある)

1. ★**読み戻し経路を先に作る。** シェーダでは printf も既存の回帰試験も使えず、
   この環境は画面収録の権限も無い。GPU出力を数値で確かめる手段が無いまま移植
   すると、間違えたときに何も分からなくなる
2. **CPU実装が正解の基準**(`client/src/ntsc.rs`)。移植の検証は CPU 出力との
   画素一致で行う。アルゴリズムはもう動いているので、移植自体は機械的
3. パス1(直交復調 + クロマLPF)から。ここが一番重く、一番素直
4. 3次元コムの履歴(`raw_p2`/`raw_p4`)はテクスチャ配列かリングにする。
   ★履歴はスロット番号で索いているので、フィールドの割り当てを変えるなら
   そこも一緒に直すこと

#### S端子ではコムが要らないことに注意

S端子(赤chのバースト検出で自動判定)では **Y は素通し、C は直交復調するだけ**で、
2次元/3次元コムも位相ドリフト補正も走らない。GPU化の効果はコンポジットの方が大きい。
逆に言えば、**S端子で使う限り復調はもう軽い**ので、GPU化を急ぐ理由は
「コンポジットも使いたい」場合に限られる。

#### 帯域を下げる案(GPU化とは別軸)

YC8 は全ライン送信なので 468 Mbps・47,000パケット/秒。内訳:

    有効映像 9.6〜62.0µs        1501サンプル  要
    カラーバースト 5.4〜7.7µs     66サンプル  要(位相基準をライン毎に測るため)
    同期チップ 0.7〜4.2µs        100サンプル  要(1 IREあたりのコード数の校正)
    バックポーチ 7.9〜9.3µs       40サンプル  要(0 IREの基準)
    その他                       113サンプル  **不要**(6.2%)

- **本当に無駄なのは 6.2%** だけ。468 → 439 Mbps にしかならない
- 効くのは **C チャネル**。3.58MHz±0.6MHz しか持たないのに 28.6MHz で運んでいる。
  ナイキストは 8.4MHz で足りるので半分に間引ける → **25%削減**(468 → 351 Mbps)。
  ただし pixfmt の追加(ゲートウェア・プロトコル・デコーダの3箇所)が要る
- ★ただし**帯域は今のところ律速ではない**。ヘッドレスでは同じ 468 Mbps で
  88万パケット lost 0。落ちるのは GUI 側の事情だった

**PCB発注前にやっておくと後で効くこと**: 1番系統(`rin_1`/`gin_1`/`sogin_1`、現在すべて
未使用終端)にS-Video用のR/Cを置いておく。既存の3つのシュントコンデンサが既にTVPピン
直近の正しい位置にあり、値を33pFに変えればアンチエイリアスとして使える。追加は0402が
9個+1×4ヘッダ+ESD1個。詳細は計画書の§5。

## 2. 個体設定をEEPROMに持たせる(MACが全基板で同じ問題を含む)

**基板には専用の不揮発領域が既に載っている。追加ハードは不要。** ゲートウェアが
まだ読んでいないだけ。

### 今の状態

    gateware/retrocastx_stream.py:34-38
    # --- ネットワーク設定(暫定; 将来はSPIフラッシュの設定ページから読む) ---
    MAC_ADDRESS = 0x025243580001   # ローカル管理アドレス "RCX"
    FPGA_IP     = "192.168.10.50"
    HOST_IP     = "192.168.10.1"
    UDP_PORT    = 34600

全部コンパイル時定数。

### ★MACの方がIPより先に問題になる

**MACアドレスが全基板で同じ `02:52:43:58:00:01`。** 同じネットワークに2枚繋ぐと
MACが衝突してスイッチの学習テーブルが壊れ、両方まともに通信できなくなる。
**IPを変えても直らない。**

24AA025E48 には**個体ごとに世界で一意な EUI-48 が工場書込みされている**ので、
読んで使えば衝突が原理的に起きない。EEPROMを載せたのはまさにこれのため。

### 使える領域

| 候補 | 場所 | 可否 |
|---|---|---|
| **24AA025E48 ×2 (U16/U17)** | I2C **0x50 / 0x51**、TVP7002と同じバス(`tvp.sda`/`tvp.scl`)、`WP`=GND で書込み許可 | **本命**。MAC領域はHW保護、**残り約250B×2 が自由** |
| i5のSPIフラッシュ | ビットストリームと同居(`bitstore.sh flash-perm` の書込み先) | 可。ただしアドレスを間違えると起動しなくなる |
| 93LC56 (U8) | FT2232HのUSB VID/PID用。FT2232H専用ピン | **不可**。FPGAから触れない |

`main.ato` の部品定義にも「MAC領域はハードウェア書込み保護済み、残り領域(~250B)は
**個体設定(IP・ボード名等)の保存に使える**」と書いてある(設計時に織り込み済み)。

### やること

1. **EUI-48を読んでMACに使う**(複数枚運用に必須。IPより先)
2. 設定ページ(IP・ボード名など)をEEPROMに置く。同じI2C経路なのでついでにできる
3. CONFIGプロトコル(type=5)で書き換えられるようにする。枠は既にある

I2Cマスタは `gateware/retrocastx_i2c.py` に実装済み(TVPを叩いている)。
アドレスを 0x50/0x51 に向けるだけで届く。

★**EUI-48がEEPROMのどのアドレスにあるかはデータシートで要確認**(末尾6バイトのはず
  だが未検証)。EEPROMのアドレスレイアウト表を先に決めること。

### IPを変えられるようにする優先度は低い

プロトコルの作り上、送信先はSUBSCRIBEの送信元から学習するのでアプリ側のIP設定は不要。
サブネットが違ってもブロードキャストで成立する(実際にそれで動いている)。
`HOST_IP` はSUBSCRIBE到着までのANNOUNCE宛先の初期値にすぎない。
ただし**基板自身のIPが固定 192.168.10.50** なので、既存ネットワークで同じアドレスが
使われていると衝突する。そのときは必要になる。

**基板の発注はブロックしない**(ハード変更不要)。

## 3. 受信バッファーの設定を利用者に要求しないようにする

**パケット落ちそのものは解決した**(NICの受信リングが既定256で溢れていた。
2048にすると 35,600 pkt/s を lost 0.0013% で捌く。経緯と測り方は
[design-notes.md](design-notes.md) の「受信の取りこぼしは NIC の受信リングだった」)。
「受信スレッドのsyscall律速」という以前の見立ては誤りで、**受信スレッドの増設も
キュー操作のまとめも不要**。

残っているのは**利用者に手作業を要求している**こと:

    Set-NetAdapterAdvancedProperty -Name 'イーサネット' -RegistryKeyword '*ReceiveBuffers' -RegistryValue 2048

これを知らないと「1.7%落ちる」「音が途切れる」状態で使うことになる。案:

- **Viewerが気づかせる**: `lost` が一定以上のときに「NICの受信バッファーを増やすと
  直ることがある」と出す。Windowsなら `Get-NetAdapterAdvancedProperty` 相当を読んで
  256のままなら名指しで警告できる(手作業を消せはしないが、迷う時間は消える)
- **README/docs に必須手順として書く**(いまは design-notes の中だけ)
- **ジャンボフレームで根本的に減らす**: 1パケットに複数ラインを詰めればパケット数が
  数分の1になり、リングの既定値でも溢れなくなる。プロトコル・ゲートウェア・スイッチ・
  NIC(いま `ジャンボパケット 無効`)の対応が必要。帯域をさらに上げるときにも要る

## 4. lost / orphan lines の追跡

長時間動かすと `lost` が少しずつ増える(13469フレームで19072パケット ≒ 0.08%)。
`orphan lines`(MODEの mode_id が一致しないLINEを捨てた数)も増える。モード切替を
繰り返したセッションで増えただけなのか、定常状態でも増えるのかを切り分ける。

**両方とも片付いた見込み(2026-08-10)**:

- `orphan`: Windows で `--headless 10` を2回。1回目はMODE到着前のLINEで 25856 まで
  増え、**MODEが確定した後は1本も増えない**。2回目(モード確定済みで開始)は
  10秒/532フレームを通して **orphan=0**。増えるのは「MODEを受け取る前/モード切替
  直後」だけで、定常状態では増えない
- `lost`: NICの受信リングが原因だった(項目1)。2048にした後は
  **2704フレーム/1,727,115パケットで lost 23 = 0.0013%**、orphan 0、
  audio underruns 0。「長時間で少しずつ増える」の主因もこれだった可能性が高い

**残り**: この 23 が何かを確定する。ボードの `seq` は**宛先に関係なく**1つずつ増える
ので、他の相手へ送ったパケット(ANNOUNCE、別ホストへのCONFIG応答)は受信側では
必ず「lost」に見える。**診断ツールを別マシンから打つと lost が増える**のはこのため。
長時間観測して増え方が「1秒に1個程度」なら ANNOUNCE の分と説明がつく。

## 5. ライン長を超える断片が0.5%

各フィールドの特定位置(413行目付近と879行目付近)に集中する。HSYNCを取り逃がした行で
`x` が長く走り、非黒範囲がライン長を超えると考えている。受信側は入る分だけ書いて
凌いでいるが、ボード側で範囲をライン長で打ち切るのが本筋。

## 6. 管面の縦横比がCPU側とシェーダ側で食い違う

`tube_aspect = 0`(管面「そのまま」= 既定)のとき、両者が別の値を使う:

- CPU側(`main.rs` の CentralPanel): 切り出し範囲の比 `cw/ch`
- シェーダ側(`render.rs` の `uniforms`): 時間ベースかつ幾何が有効なら **4:3 固定**

描画callbackの矩形はCPU側の比で確保されるので、実際に映る管面はその中で
レターボックス/ピラーボックスされる。`画に合わせる` はCPU側の比でウィンドウを
決めるため、押しても管面はぴったり収まらない。

外側の色を撤去して黒に統一したので見た目には出ないが、比の計算が2か所にあること
自体が原因。本筋はシェーダに `avail` 全体を渡して管面の形をシェーダだけに決めさせ、
`画に合わせる` 用に描画サイズを返してもらうこと。

## 7. モニタプロファイル

`mon.15` / `mon.24` / `mon.31` に [H幅, H位置, V幅, V位置] を持つ。実CRTのつまみに
相当し、スライダーで合わせる。将来は CZ-600D / CZ-612D のような実在モニタの
プロファイルを外部ファイルにする案がある(オーバースキャン量、走査線の強さなど)。

信号は左右非対称(バックポーチが長い)なので `H位置 0` だと絵が右に寄る。
実測例: 15kHz Mode7 は `active 994x480 at (157,33)`, htotal 1179 → 適正な H位置は
(157 + 994/2)/1179 - 0.5 = +0.055。

## 9. pll_divide の自動決定(部分的に完了)

`自動調整` ボタン(Viewer)と `pll_tune autotune`(CLI)がある。上限まで過剰サンプルして
スペクトル占有率から倍率を割り出し、8の倍数で±7%だけ局所探索する。24kHzで真値1408に
着地することを確認済み。

**映像ソースのプロファイル方式を追加した**(Viewerの `映像ソース` プルダウン)。fH と
ドットクロック候補から htotal を決めるので、絵の内容を一切見ない。X68000 の3帯域で
正解する(回帰テストあり)。原理と選び方の落とし穴は design-notes.md 参照。

未対応:
- VGA / PC-9801 のプロファイルは数値の裏を取っていない(実機で確認が必要)
- スペクトル探索の `自動調整` は残してある。プロファイルで pll_divide を決めてから
  位相だけを振る形に整理するとよい
- 誤った状態(PLLが外れている、絵が真っ暗など)から始めると失敗する。開始前に
  健全性を確認する仕組みが無い
- TVPのピクセルクロック下限(12MHz)により1:1にできないモードがある(15kHz 512x512 は
  本来の htotal 608 = 9.72MHz なので2倍の1216を使う)。下限を満たす最小の整数倍を
  選ぶ処理は入っているが、実機での検証は24kHzのみ

## 参考: 現在の設計の要点

**幾何は同期信号だけで決まり、絵の内容に依存しない。**

```
水平位置 = (offset_px + k) / htotal      offset_px はライン内の絶対位置
垂直位置 = スロット / (slot_k × vtotal)   slot_k は mflags bit0 で伝える
```

**インターレースは設定ではなく測定で決まる。**

```
TVPの検出ビット(38h bit5)      インターレースかどうか
生VSYNCの半ライン位相          どちらのフィールドが下か(次のHSYNCまでが短い側が上)
TVP vtotal / 生ライン数の比    フィールド単位かフレーム単位か
```

**生同期(P4 pin155=HSYNC / pin153=VSYNC)は sysドメインで測る。** pll_divide に依存
しない絶対値が得られる(key 0x2A/0x2B/0x2C)。TVPのHSOUT/VSOUT経由の値は、TVPが
インターレースのVSYNCを間引くのでフレーム単位に畳まれている。

**pll_divide はドットクロック再生専用で、描画位置に影響しない。** hs_offset は
設定項目から撤去済み(既定0)。
