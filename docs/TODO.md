### 入れたもの

- CONFIGキー **0x36**(pixfmt)/ **0x5E**(クランプ選択 reg10h[2:0])/
  **0x5F**(粗ゲイン reg1Bh=B/G)/ **0x65**(粗オフセット reg1Fh=G)/
  **0x67**(粗ゲイン reg1Ch=**R**)/ **0x68**(粗オフセット reg20h=R)/
  **0x69**(入力MUX reg19h)
- **pixfmt 3 = YC8**(2B/px、下位=緑ch8bit=CVBS/Y、上位=赤ch8bit=S端子のC)。
  2B/pxのままなので断片化もMTU計算も既存と同一。ViewerはYをグレースケールで出す
- `retrocastx.videoin` — 方式の一括切替・自動判別・**波形の実測判定**

★**1Bh と 1Ch はビット割りが違う**(1Bh=`[7:4]G [3:0]B` / 1Ch=`[7:4]予約 [3:0]R`)。
同じ1.2倍でも 0x77 と 0x07。S端子のCは赤chなので 1Ch が要る。

### S端子は既存のD-SUB経路で試せる

計画書 §7 の「1番系統に部品を足す」は**専用コネクタを付けるための話**で、前提条件では
ない。R/G/Bは同一の前段(75Ω+100nF+220Ω/33pF)なので、**Y→緑 / C→赤**で今日試せる。
Yを緑に入れるのは固定(SOGタップが緑にしか無い)。
YとCで独立にクランプとゲインを持てるぶん、輝度もクロマも**約2.4倍**の分解能になり、
なにより**Y/C分離が丸ごと不要**になる(Step 4 の一番難しい部分が消える)。

### 当初の計画から変わった点(重要)

- **ミッドレベルクランプ単独では成立しない。粗ゲインを同時に下げる。**
  ブランキングが512に座るので白側ヘッドルームが半分になり、既定の1.2倍のままでは
  コンポジット(1Vpp=140IRE)が飽和する。`1Bh = 0x07`(0.5倍)が出発点
- **バーストは73コードにはならない。36コードが上限**(ヘッドルーム半減のぶん)。
  それでもRGB555の4〜5段階よりは4倍以上良い
- ボトムレベルクランプでもブランキングは0ではなく**約64**(粗オフセット1Fhの既定)
- **粗オフセット(1Fh)でブランキングを動かす別解は成立しない。** 粗クランプは
  既定で無効(reg 2Dh)で、ファインクランプの帰還ループがADC前のオフセットを
  打ち消す。実測で +64→+0→-32 と振ってもブランキングが動かなかった。
  白の飽和に効いたのは**ファインゲイン(09h)**(33=1.129倍が掛かっていた)
- **「絵が出た」では合否が判定できない。** ボトムレベルならバーストの下半分が消え、
  ゲイン過大なら白が飽和する。どちらも絵は出る。だから `probe` で数値を見る

### Y/C分離は 3次元(動き適応フレームコム)まで実装した

    1次元  水平のみ(BPF/トラップ)          メモリ不要
    2次元  + 垂直(ラインコム)               1H
    3次元  + 時間(フレームコム、動き適応)  1フレーム  ← いまここ

★用語注意: 英語圏の "1H comb / 1D comb" は上下ラインを使うものを指すが、
**日本語の「1次元」は水平のみ**を指す。当初この文書は英語の言い方で
「1Dコム」と書いていたので、日本語の2次元/3次元に統一した。

**成立の根拠(実測)。** NTSCは1フレームあたり 525×227.5 = 119437.5周期で
端数0.5周期なので、1フレームで位相が180°反転する。ボードの「フレーム」は
1フィールドなので同じライン番号は2フレームおきに来る:

| ボードのフレーム差 | NTSCフレーム差 | 位相差(n=4576) | 用途 |
|---|---|---|---|
| 2 | 1 | **175.8°** | フレームコム(C を取る) |
| 4 | 2 | **4.2°** | **動き検出**(クロマが混ざらない) |

★**動き検出に1フレーム前を使ってはいけない。** 位相180°なのでクロマが差に
そのまま出て、色のある所が全部「動いている」ことになる(映像域の副搬送波成分で
9315 対 388)。2フレーム前なら位相が同じなのでクロマが消え、純粋な輝度の時間差になる。

**効果(同じフレームを両方式で復調、15フレーム平均)**:

| | 2次元 | 3次元 | |
|---|---|---|---|
| 垂直detail上位10%の彩度(偽色) | 0.1523 | **0.1447** | −0.0076 |
| 平坦部の彩度のσ(ノイズ) | 0.2583 | **0.2477** | −0.0106 |

静止部分ではフレームコムが厳密解なので、フレーム差を取っても**クロマはむしろ
綺麗になる**(ノイズが増えるという当初の懸念は外れた)。

負荷は 1コアの 15.4% → **19.6%**(M4 Pro、シングルスレッド、release)。
メモリは履歴2面ぶん +3.8MB。

実機: 263行すべてが3次元、動きと判定されたのは 1.4〜2.4%、lost 0。

### 残っているのは GPU化 ← **次のセッションの主題**

CPU実装は 2次元/3次元コム・位相ドリフト補正・S端子まで揃っていて、実機で
安定して動いている。次は GPU オフロード。

#### なぜやるか(動機が1つ増えた)

1. **CPU負荷**: 1フィールド 3.85ms = 1コアの23%(`cargo test --release --
   --ignored --nocapture ntsc::tests::timing` で測れる)
2. **転送量**: 生サンプルを送る方が半分(1.9MB/フィールド 対 いまのRGBA 3.8MB)
3. ★**publish の揺らぎが減る**(2026-08-15に判明)。表示できる新フレームの割合は
   **到着の揺らぎ σ で決まり**、その σ = 4.35ms は復調時間 3.85ms とほぼ同じ。
   publish のタイミングが処理時間のばらつきを引き継いでいる。
   **復調を軽くするのは、見に行く回数を上げるのと同じ効果を持つ。**
   根拠と確率モデルは [design-notes.md](design-notes.md)「表示レートは
   『見に行く回数』で決まる」

#### 進め方(順序に理由がある)

1. ★**読み戻し経路を先に作る。** シェーダでは printf も既存の回帰試験も使えず、
   この環境は画面収録の権限も無い。GPU出力を数値で確かめる手段が無いまま移植
   すると、間違えたときに何も分からなくなる
2. **CPU実装が正解の基準**(`client/src/ntsc.rs`)。移植の検証は CPU 出力との
   画素一致で行う。アルゴリズムはもう動いているので、移植自体は機械的
3. パス1(直交復調 + クロマLPF)から。ここが一番重く、一番素直
4. 3次元コムの履歴(`raw_p2`/`raw_p4`)はテクスチャ配列かリングにする。
   ★履歴はスロット番号で索いているので、フィールドの割り当てを変えるなら
   そこも一緒に直すこと

#### S端子ではコムが要らないことに注意

S端子(赤chのバースト検出で自動判定)では **Y は素通し、C は直交復調するだけ**で、
2次元/3次元コムも位相ドリフト補正も走らない。GPU化の効果はコンポジットの方が大きい。
逆に言えば、**S端子で使う限り復調はもう軽い**ので、GPU化を急ぐ理由は
「コンポジットも使いたい」場合に限られる。

#### 帯域を下げる案(GPU化とは別軸)

YC8 は全ライン送信なので 468 Mbps・47,000パケット/秒。内訳:

    有効映像 9.6〜62.0µs        1501サンプル  要
    カラーバースト 5.4〜7.7µs     66サンプル  要(位相基準をライン毎に測るため)
    同期チップ 0.7〜4.2µs        100サンプル  要(1 IREあたりのコード数の校正)
    バックポーチ 7.9〜9.3µs       40サンプル  要(0 IREの基準)
    その他                       113サンプル  **不要**(6.2%)

- **本当に無駄なのは 6.2%** だけ。468 → 439 Mbps にしかならない
- 効くのは **C チャネル**。3.58MHz±0.6MHz しか持たないのに 28.6MHz で運んでいる。
  ナイキストは 8.4MHz で足りるので半分に間引ける → **25%削減**(468 → 351 Mbps)。
  ただし pixfmt の追加(ゲートウェア・プロトコル・デコーダの3箇所)が要る
- ★ただし**帯域は今のところ律速ではない**。ヘッドレスでは同じ 468 Mbps で
  88万パケット lost 0。落ちるのは GUI 側の事情だった

**PCB発注前にやっておくと後で効くこと**: 1番系統(`rin_1`/`gin_1`/`sogin_1`、現在すべて
未使用終端)にS-Video用のR/Cを置いておく。既存の3つのシュントコンデンサが既にTVPピン
直近の正しい位置にあり、値を33pFに変えればアンチエイリアスとして使える。追加は0402が
9個+1×4ヘッダ+ESD1個。詳細は計画書の§5。

## 2. 個体設定をEEPROMに持たせる(MACが全基板で同じ問題を含む)

**基板には専用の不揮発領域が既に載っている。追加ハードは不要。** ゲートウェアが
まだ読んでいないだけ。

### 今の状態

    gateware/retrocastx_stream.py:34-38
    # --- ネットワーク設定(暫定; 将来はSPIフラッシュの設定ページから読む) ---
    MAC_ADDRESS = 0x025243580001   # ローカル管理アドレス "RCX"
    FPGA_IP     = "192.168.10.50"
    HOST_IP     = "192.168.10.1"
    UDP_PORT    = 34600

全部コンパイル時定数。

### ★MACの方がIPより先に問題になる

**MACアドレスが全基板で同じ `02:52:43:58:00:01`。** 同じネットワークに2枚繋ぐと
MACが衝突してスイッチの学習テーブルが壊れ、両方まともに通信できなくなる。
**IPを変えても直らない。**

24AA025E48 には**個体ごとに世界で一意な EUI-48 が工場書込みされている**ので、
読んで使えば衝突が原理的に起きない。EEPROMを載せたのはまさにこれのため。

### 使える領域

| 候補 | 場所 | 可否 |
|---|---|---|
| **24AA025E48 ×2 (U16/U17)** | I2C **0x50 / 0x51**、TVP7002と同じバス(`tvp.sda`/`tvp.scl`)、`WP`=GND で書込み許可 | **本命**。MAC領域はHW保護、**残り約250B×2 が自由** |
| i5のSPIフラッシュ | ビットストリームと同居(`bitstore.sh flash-perm` の書込み先) | 可。ただしアドレスを間違えると起動しなくなる |
| 93LC56 (U8) | FT2232HのUSB VID/PID用。FT2232H専用ピン | **不可**。FPGAから触れない |

`main.ato` の部品定義にも「MAC領域はハードウェア書込み保護済み、残り領域(~250B)は
**個体設定(IP・ボード名等)の保存に使える**」と書いてある(設計時に織り込み済み)。

### やること

1. **EUI-48を読んでMACに使う**(複数枚運用に必須。IPより先)
2. 設定ページ(IP・ボード名など)をEEPROMに置く。同じI2C経路なのでついでにできる
3. CONFIGプロトコル(type=5)で書き換えられるようにする。枠は既にある

I2Cマスタは `gateware/retrocastx_i2c.py` に実装済み(TVPを叩いている)。
アドレスを 0x50/0x51 に向けるだけで届く。

★**EUI-48がEEPROMのどのアドレスにあるかはデータシートで要確認**(末尾6バイトのはず
  だが未検証)。EEPROMのアドレスレイアウト表を先に決めること。

### IPを変えられるようにする優先度は低い

プロトコルの作り上、送信先はSUBSCRIBEの送信元から学習するのでアプリ側のIP設定は不要。
サブネットが違ってもブロードキャストで成立する(実際にそれで動いている)。
`HOST_IP` はSUBSCRIBE到着までのANNOUNCE宛先の初期値にすぎない。
ただし**基板自身のIPが固定 192.168.10.50** なので、既存ネットワークで同じアドレスが
使われていると衝突する。そのときは必要になる。

**基板の発注はブロックしない**(ハード変更不要)。

## 3. 受信バッファーの設定を利用者に要求しないようにする

**パケット落ちそのものは解決した**(NICの受信リングが既定256で溢れていた。
2048にすると 35,600 pkt/s を lost 0.0013% で捌く。経緯と測り方は
[design-notes.md](design-notes.md) の「受信の取りこぼしは NIC の受信リングだった」)。
「受信スレッドのsyscall律速」という以前の見立ては誤りで、**受信スレッドの増設も
キュー操作のまとめも不要**。

残っているのは**利用者に手作業を要求している**こと:

    Set-NetAdapterAdvancedProperty -Name 'イーサネット' -RegistryKeyword '*ReceiveBuffers' -RegistryValue 2048

これを知らないと「1.7%落ちる」「音が途切れる」状態で使うことになる。案:

- **Viewerが気づかせる**: `lost` が一定以上のときに「NICの受信バッファーを増やすと
  直ることがある」と出す。Windowsなら `Get-NetAdapterAdvancedProperty` 相当を読んで
  256のままなら名指しで警告できる(手作業を消せはしないが、迷う時間は消える)
- **README/docs に必須手順として書く**(いまは design-notes の中だけ)
- **ジャンボフレームで根本的に減らす**: 1パケットに複数ラインを詰めればパケット数が
  数分の1になり、リングの既定値でも溢れなくなる。プロトコル・ゲートウェア・スイッチ・
  NIC(いま `ジャンボパケット 無効`)の対応が必要。帯域をさらに上げるときにも要る

## 4. lost / orphan lines の追跡

長時間動かすと `lost` が少しずつ増える(13469フレームで19072パケット ≒ 0.08%)。
`orphan lines`(MODEの mode_id が一致しないLINEを捨てた数)も増える。モード切替を
繰り返したセッションで増えただけなのか、定常状態でも増えるのかを切り分ける。

**両方とも片付いた見込み(2026-08-10)**:

- `orphan`: Windows で `--headless 10` を2回。1回目はMODE到着前のLINEで 25856 まで
  増え、**MODEが確定した後は1本も増えない**。2回目(モード確定済みで開始)は
  10秒/532フレームを通して **orphan=0**。増えるのは「MODEを受け取る前/モード切替
  直後」だけで、定常状態では増えない
- `lost`: NICの受信リングが原因だった(項目1)。2048にした後は
  **2704フレーム/1,727,115パケットで lost 23 = 0.0013%**、orphan 0、
  audio underruns 0。「長時間で少しずつ増える」の主因もこれだった可能性が高い

**残り**: この 23 が何かを確定する。ボードの `seq` は**宛先に関係なく**1つずつ増える
ので、他の相手へ送ったパケット(ANNOUNCE、別ホストへのCONFIG応答)は受信側では
必ず「lost」に見える。**診断ツールを別マシンから打つと lost が増える**のはこのため。
長時間観測して増え方が「1秒に1個程度」なら ANNOUNCE の分と説明がつく。

## 5. ライン長を超える断片が0.5%

各フィールドの特定位置(413行目付近と879行目付近)に集中する。HSYNCを取り逃がした行で
`x` が長く走り、非黒範囲がライン長を超えると考えている。受信側は入る分だけ書いて
凌いでいるが、ボード側で範囲をライン長で打ち切るのが本筋。

## 6. 管面の縦横比がCPU側とシェーダ側で食い違う

`tube_aspect = 0`(管面「そのまま」= 既定)のとき、両者が別の値を使う:

- CPU側(`main.rs` の CentralPanel): 切り出し範囲の比 `cw/ch`
- シェーダ側(`render.rs` の `uniforms`): 時間ベースかつ幾何が有効なら **4:3 固定**

描画callbackの矩形はCPU側の比で確保されるので、実際に映る管面はその中で
レターボックス/ピラーボックスされる。`画に合わせる` はCPU側の比でウィンドウを
決めるため、押しても管面はぴったり収まらない。

外側の色を撤去して黒に統一したので見た目には出ないが、比の計算が2か所にあること
自体が原因。本筋はシェーダに `avail` 全体を渡して管面の形をシェーダだけに決めさせ、
`画に合わせる` 用に描画サイズを返してもらうこと。

## 7. モニタプロファイル

`mon.15` / `mon.24` / `mon.31` に [H幅, H位置, V幅, V位置] を持つ。実CRTのつまみに
相当し、スライダーで合わせる。将来は CZ-600D / CZ-612D のような実在モニタの
プロファイルを外部ファイルにする案がある(オーバースキャン量、走査線の強さなど)。

信号は左右非対称(バックポーチが長い)なので `H位置 0` だと絵が右に寄る。
実測例: 15kHz Mode7 は `active 994x480 at (157,33)`, htotal 1179 → 適正な H位置は
(157 + 994/2)/1179 - 0.5 = +0.055。

## 9. pll_divide の自動決定(部分的に完了)

Viewer には3つの決め方がある。**上から順に試す**のがよい。

| | 絵を見るか | かかる時間 | 何をするか |
|---|---|---|---|
| `適用`(映像ソースの右) | 見ない | 一瞬 | fH と水晶/分周から htotal を計算。迷ったら大きい側 |
| `簡易スキャン` | 見る | 20秒ほど | **プロファイルが許す候補だけ**を測って選び、位相も振る |
| `フルスキャン` | 見る | 40秒ほど | 候補を前提にせず総当たり。未知の機種向け |

`適用` は絵の内容に一切依存しないので真っ黒でも当たるが、**同じ fH を作れる
ドットクロックが複数あると決め切れない**。X68000の31.5kHz がそれで、768x512(htotal
1104)・512x512(736)・HRL付き(552)が全部 fH 31.500kHz ちょうど。`適用` は安全側の
最大値(1104)を返すため、512x512 では1.5倍オーバーサンプルのままになる。

`簡易スキャン` はその候補集合(この例では htotal 368/552/736/1104 の4点、設定値
としては 552/736/1104 の3通り)**全部**の位相感度を測り、いちばん感度が強い
(最悪÷最良がいちばん小さい)点を採る。どれもしきい値を下回らなければ判別できて
いないので、いちばん大きい側(=過剰サンプル。眠いだけで壊れない)に倒す。
採用したら位相を1刻みで5点詰める。結果には候補ごとの位相感度を並べる。

★**「感度が立った最初の候補で止まり、降りる先を占有率で枝刈りする」形は実機で
  外した**(2026-09-04、31.5kHz の 512x512 で 1104 のまま動かず、降下が一度も
  起きていなかった)。枝刈りの根拠は「`設定値 × 占有率` は真の htotal の下限」
  だったが成り立っていなかった。真値 736 を 1104 で測ったときの占有率の理論上の
  上限は 736/1104 = 0.667 なのに実測は 0.716 出る(99%エネルギーの裾がノイズを
  拾う)。下限として使えない量で枝刈りしていたので、正解が候補から消えていた。

  判定材料の側は十分な差が出ていた(実測、真値736):

```text
    pll 1104  最良 160.25  最悪 156.58  → 98%   1.5倍オーバーサンプル
    pll  736  最良 377.11  最悪 200.92  → 53%   ★1:1
    pll  552  最良 406.15  最悪 351.23  → 87%
```

  **鮮鋭度の絶対値では選べない**(552 の最良 406 は 736 の 377 より大きい)。
  見るのは同じ設定内での比。この実測値は `quick_pick` の試験に固定してある。

★**占有率で1:1を判定してはいけない。** 一度これで実装して実機で外した
  (768x512 で 736 が選ばれた)。占有率は「1:1ならスペクトルがNyquistまで埋まる」を
  前提にするが、768x512(34.776MHz)は1ドットが白の64%までしか立たないので、
  正解の1104で測っても占有率は0.7程度。`1104 × 0.7 = 773` から736が近く見える。
  1.0倍と1.5倍を占有率で見分けるのはこの機種では原理的に無理。
  占有率は `設定値 × 占有率 = 真のhtotal × 帯域率` なので**下限**としてだけ使う
  (降りる先の枝刈り)。どの候補でも感度が立たなかったときは推測せず、
  いちばん大きい候補に戻す。

候補は**水晶の一族**でも絞る(`best()` と同じ相対誤差の判定)。15.98kHz で
69.552/4 → htotal 1088 が8の倍数のせいで残ると、正解の608(pll 1216)と1.79倍という
絵では見分けにくい相手になる。相対誤差は 9.2e-5 対 1.2e-6 と80倍違うので、
信号の側で落とす。結果、15kHz帯は候補が pll 1216 の1通りだけになる。

★候補は `profiles.rs` の水晶/分周表と fH だけから作る(`scan_candidates`)。
  **機種固有の分岐はスキャン側に一切無い**ので、機種を足すときは表を書くだけでよい。

X68000のドットクロック表は XEiJ の CRTC.java から起こした
(<https://stdkmd.net/xeij/source/xeij-CRTC.java.htm>)。69.552MHz の /2,3,4,6,8、
38.864MHz の /4,8、50.3498MHz の /2 で全モードを説明できる。

未対応:
- VGA / PC-9801 のプロファイルは数値の裏を取っていない(実機で確認が必要)
- `簡易スキャン` の位相感度版は実機で未検証(2026-09-03 時点。回帰テストのみ)。
  判定のしきい値 `PHASE_SENSITIVE = 0.85` はフルスキャン側で実機から決めた値を
  流用している。1段降りるかどうかがこの1つの数字で決まるので、実機で外すようなら
  ここを見る
- 誤った状態(PLLが外れている、絵が真っ暗など)から始めると失敗する。開始前に
  健全性を確認する仕組みが無い。ただし簡易スキャンは失敗しても最大の候補
  (=過剰サンプル)に留まるので、絵が壊れる方へは倒れない
- TVPのピクセルクロック下限(12MHz)により1:1にできないモードがある(15kHz 512x512 は
  本来の htotal 608 = 9.72MHz なので2倍の1216を使う)。簡易スキャンはこれを
  「×2オーバーサンプル」として報告する(位相感度が弱いのは異常ではない)
- CLI の `pll_tune autotune` は総当たり版のまま。簡易スキャンは移植していない

## 9b. インターレースの織り込み(2026-09-03 解決)

24kHz 1024x848 で**2つのフィールドが交互ではなく上下に積まれる**症状があった。
原因は「そもそもインターレースか」の判定を **TVPのP/I検出(reg 38h bit5)単独**に
任せていたこと。このビットはX68000の24kHzを progressive と誤答する
(実測 0x57=0x21。reg22h bit0 を立ててVSOUTをフィールドごとにしても変わらない)。
`il_det` が 0 だと `fld_pos` も `in_f2` も 0 に固定され、織り込みが丸ごと止まる。

**生同期はちゃんと動いていた。** 同じときの実測:

```
0x2A FH_RAW    = 24698 Hz      0x2C LINES_RAW = 466(=1フィールド)
0x2B FV_RAW    = 53.125 Hz     0x24 VS_X_RAW  = 715/11 を 106:94 で交互(差704 = 周期の半分)
```

直したのは3つ。

1. **`il_det` を生同期とTVPのORにした**(`retrocastx_capture.py`)。生VSYNCの半ライン
   位相が交互かどうかで判定する `il_raw` を足した。ORなのは、TVPが検出できている
   帯域の挙動を変えないため。判定はヒステリシス付き(12でセット/4でクリア)。
   切り分け用に CONFIG key **0x2D** で内訳を読める
   (bit0=生位相が交互 bit1=生同期OK bit2=TVPのP/I bit3=TVP vtotalが2フィールド分)。
2. **`field_invert`(0x66)= 1 をX68000プロファイルに入れた。** 生位相の符号が逆だった。
   実測の織り込みのずれ: 0 → 17.5 / 1 → 0.68。
3. **`sync_ctl2`(0x5B、reg22h)= 0x09 をX68000プロファイルに入れた。**
   VSOUTをフィールドごとに出させる。既定0x08だとVSOUTが2フィールドに1回になり、
   捕捉側が vtotal/2 = 465 で折り返す。折り返し点は固定なのに実フィールド長は
   半ラインのぶん465と466で1行違うので、片方が必ず1行ずれる(細い斜線が破線状に崩れる)。
   実測の織り込みのずれ: 0x08 → 4.59〜4.95 / 0x09 → 1.39〜1.44(各3回、再現あり)。

`sim_capture_interlace.py` に**この経路を通すケースを追加した**。既存の3ケースは
どれも生同期の無い構成で、生同期からの判定は一度も検証されていなかった。
新ケースは `cfg_il_detect = 0`(TVPが誤答している状況)で生VSYNCだけを与える。

未確認:
- 15kHz のインターレース(CRTMOD $01 など)で `field_invert=1` / `sync_ctl2=0x09` が
  正しいか。X68000プロファイル全体に効くので、モードを変えて確かめること
- MSX / コンポジット / S端子は `sync_ctl2` を既定0x08のままにしてある。reg22hの
  コメントにある「MSXの262ライン progressive が双安定になる」問題は 0x09 で
  直るはずだが未実測

## 10. v1.0 基板で直すこと(v0.9.0 で見つかった軽微な不具合)

どれも v0.9.0 の動作には影響しない。次に基板を作るときに直す。

### 10-1. RJ45 に ETH1/ETH2 のシルクを入れる

基板上でどちらのポートがどちらか判別できない。しかも呼び名が資料間で逆なので
混乱しやすい(詳細は `hardware/adc-frontend/README.md` の
「GbE 差動ペアの対応」節)。

```
J11 (上側)  eth2_* = SO-DIMM 偶数ピン  ← 本リポジトリの流儀では ETH2 = PHY0 = litex eth1
J12 (下側)  eth1_* = SO-DIMM 奇数ピン
```

**差動ペアの配線自体は検証済みで正しい**(2026-08-19、データシート + i5ether +
rainbow-board の3点照合)。ラベルだけの問題。

### 10-2. センタータップのネット名の入れ違いを直す

```
main.ato:1933  eth.jack.ct.override_net_name  = "eth1_ct"   ← jack は eth2_* を運ぶ
main.ato:1934  eth.jack2.ct.override_net_name = "eth2_ct"   ← jack2 は eth1_*
```

各ポートに独立した 100nF が付いているので電気的には無害。名前が逆なだけ。

### 10-3. J8(S/PDIF光受信)の周辺を配線し直す

PLR135/T10 → PLR135/T へ変更した際、ランドが変わって既存配線が使えなくなった
(取付穴 φ1.15→φ3.20、間隔 5.08→7.62mm)。v0.9.0 では配線済みだが、
配置の余裕は少ない。

### 10-4. ポゴピン(PG1-PG4)の高さを実測値で確定する

`tools/order_sourcing.json` に書いたとおり、基板〜モジュール裏の間隙 2.6mm は
推定値でソケット種により変動する。**v0.9.0 の実機で測ってから**発注すること。
これが無いと基板上の CH347F から FPGA へ JTAG が届かない(必須部品)。

### 10-5b. 未使用時の同期入力が浮かないようにする(プルダウン)

D-SUB の HSYNC/VSYNC は、コンポジット/S端子/MSX を使っているとき**何も繋がらない**。
5Vトレラントのシュミットバッファ(`buf_sync` = SN74LVC2G17)の入力が浮くと自己発振し、
捕捉側の `raw_ok`(生同期の周期が `(64, 0xF000)` に入るか)が**誤って立つ**。すると
存在しない同期の位相でフィールド極性が決まり、**両フィールドが同じスロットに交互に
上書きされて絵が1ライン上下に震える**(実機 2026-09-06、コンポジット480i。
`il: raw0 rawok1 P/I1 frame0` / `SOG lowmax 773` = SOG経路は健全だった)。

ゲートウェア側は CONFIG key `0x6A`(`no_raw_phase`)で分岐ごと外せるようにしたので
v0.9.0 でも回避できるが、**根本は入力が浮いていること**。第2入力の HSYNC/VSYNC
(`buf_sync2`)も同じ。次に基板を作るときに各入力へプルダウン(10kΩ程度)を入れる。

同じ罠は `syncdet`(何も繋がっていない SOGIN でも SOGD=1 を返す)でも踏んでいる。
**浮いた入力は「無信号」ではなく「それらしい信号」を出す**と考えること。

### 10-5. S端子とコンポジットを別ジャックにして、Y/CVBS を1個のスイッチで切り替える

いまは S端子とコンポジットが同じ J5(2x4ボックスヘッダ、TVPの1番系統)を共有していて、
コンポジットは **pin1 = Y ピン**に芯線を入れる(`parts/_mech/mech.ato:352`)。
同期タップが Y 側にしか無い(`main.ato:1313` で Y から SOGIN_1 へ分岐)ためで、
C ピンに入れても同期が取れない。

v1.0 で別ジャックにするなら、**同時挿しを防ぐのに物理スイッチは要らない。**
同期タップは `ch_y` を通す前の生ノードから分岐しているので、そこを切り替えれば
映像と同期が同時に切り替わる。**切るべき信号は Y/CVBS の1本だけ**で足りる。

```
S端子Y ──── 75Ω ──┐
                  ├── SPDT ── 選択ノード ──┬── 100nF ─ 220Ω ─ 33pF ── GIN_1
コンポジット ─ 75Ω ──┘                      └── 100nF ─ 220Ω ────── SOGIN_1
                        ↑
                    FPGAのGPIO 1本(CONFIGキーで叩く)
```

C(→RIN_1)は S端子しか使わないので競合せず、切り替え不要。19h も `MUX_ALL1` の
ままでよい。`profiles.rs` の `input_regs` に切り替えキーを1つ足せば、Viewer で
映像ソースを選んだ瞬間にレジスタとスイッチが同時に動く。**物理スイッチだと
「設定はコンポジットなのにスイッチはS端子側」という食い違いが作れてしまう**ので、
そちらの方が失敗モードが多い(同じ形の失敗は `all_input_modes_write_the_same_keys`
で防いでいる類のもの)。

気をつける点:

1. **75Ω終端はジャック側へ移す。** いま `VideoInputChannel` の中に入っている
   (`main.ato:517`)。スイッチ手前に置くなら共有側の 75Ω は外す。両方あると
   合計 37.5Ω で振幅が半分になる。
2. **未選択側も終端する。** スイッチのオフ容量(数pF)経由で漏れ込む。5pF・3.58MHz
   で約8.9kΩ、概算 -42dB。未終端だと送り出しが開放を見て2倍振幅になり漏れも2倍
   (1Vppに対して1.6% = 8bitで4LSB程度)。オフアイソレーションの高い品種を選ぶ。
3. **スイッチはS端子側にも入る。** S端子は独立したCチャンネルを持つぶんクロマ
   分解能がコンポジットの約4倍あり(`mech.ato:355`)、2入力のうち品質の高い方。
   Ron の小さい品種にする(NX3L1G384 / TS5A3160 は Ron 1Ω以下で直列220Ωに対して
   無視できる。74LVC1G3157 は 10Ω前後で振幅5%弱の一定損失 + Ron変動による歪み)。
   D-SUB(X68000)は3番系統でこの経路を通らないので影響しない。

★**GIN_4(pin 96)が空いている。** 19h は `[3:2]=11` で GIN_4 を選べる
(`retrocastx_i2c.py:170`。RIN/BIN/SOGIN は3本ずつで全部埋まっているが、Green だけ
4本ある)。当初はコンポジットを GIN_4 へ入れて 19h で切り替える案を検討したが、
**同期用の SOGIN_4 が存在しない**ので結局スイッチが要る。上の案なら1個で映像も
同期も片付くので GIN_4 は使わない。将来の入力用に空けておく。

## 参考: 現在の設計の要点

**幾何は同期信号だけで決まり、絵の内容に依存しない。**

```
水平位置 = (offset_px + k) / htotal      offset_px はライン内の絶対位置
垂直位置 = スロット / (slot_k × vtotal)   slot_k は mflags bit0 で伝える
```

**インターレースは設定ではなく測定で決まる。**

```
TVPの検出ビット(38h bit5) OR 生VSYNCの位相の交互性   インターレースかどうか
生VSYNCの半ライン位相      どちらのフィールドが下か(次のHSYNCまでが短い側が上)
TVP vtotal / 生ライン数の比 フィールド単位かフレーム単位か
```

★**「インターレースかどうか」を TVP の検出ビット単独に任せてはいけない。**
X68000 の 24kHz 1024x848 を progressive と誤答する(実測 0x57=0x21)。生VSYNCの
半ライン位相が交互かどうかを OR で足してある。内訳は key 0x2D で読める。経緯は 9b。

**SUBSCRIBE は各NICのサブネット宛へ出す。限定ブロードキャストは使わない。**

```
en0 192.168.11.24  → 192.168.11.255 へ2秒ごと
utun*/lo0          → 除外(point-to-point は broadcast を持たない)
```

255.255.255.255 はサブネット経路を持たないので既定経路に載る。既定経路が
point-to-point の VPN トンネルだと送信元アドレスを割り当てられず、
`Can't assign requested address` で**送信そのものが失敗する**。`.app` には
`--bind` を渡せないので、VPN接続中は接続できなかった(2026-09-04)。

サブネット宛なら経路がそのNICのサブネット経路に決まるので既定経路を参照しない。
実測: VPN接続のまま `--bind` 無しで 644フレーム / 58.8Mbps / lost 0。
ボードと別サブネット(ボード 192.168.10.50 / PC 192.168.11.24)でも届く。
NICの列挙は `if-addrs` で、Windows も同じコードで動く。

送信が1つも通らなかったときは `Shared::net_error` に理由を入れてUIへ出す。
**以前は `let _ =` で捨てていたので、症状が「何も映らない」だけだった。**

`host/python` 側は `retrocastx/netutil.py` に同じ判定を寄せてある。NICの列挙は
psutil を使い、無ければ限定ブロードキャストに落ちる(= VPN下では従来どおり
失敗するので `--bind` が要る)。標準ライブラリには getifaddrs 相当が無いため。
ボードへ送る7つのツール(`discover` / `cfg` / `pll_tune` / `line_probe` /
`span_check` / `videoin` / `vs_probe`)は全部対応済みで、`--board` も `--bind` も
省略できる。引数の宣言は `netutil.add_args()` に寄せて文言を揃えてある。
**送信の失敗でプログラムを終わらせない**のも要点で、ボードはANNOUNCEを毎秒
自発送出するので probe が出せなくても受動リッスンで見つかる。

**生同期(P4 pin155=HSYNC / pin153=VSYNC)は sysドメインで測る。** pll_divide に依存
しない絶対値が得られる(key 0x2A/0x2B/0x2C)。TVPのHSOUT/VSOUT経由の値は、TVPが
インターレースのVSYNCを間引くのでフレーム単位に畳まれている。

**pll_divide はドットクロック再生専用で、描画位置に影響しない。** hs_offset は
設定項目から撤去済み(既定0)。
