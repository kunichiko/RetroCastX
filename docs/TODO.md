## 1. 切り分け用の暫定値を戻す(行欠け/横ずれの修正の後片付け)

原因は解決した(下記)。残っているのは切り分けのために大きくした値を戻すこと。

- `retrocastx_stream.py` の `nface=16` → 8、`fifo_depth=8` → 4
- どちらも「範囲の遅れが fifo_depth に比例する」ことを示すために振った値で、
  修正後は根拠がない。BRAMは余っているので害はないが残すべきではない
- 戻したら `span_check` で 100% を再確認する(ビルド+焼き直しが1回)

**解決済みの内容(記録)**: 症状は当初「全幅の明るい横線の直後3行が2サンプル早く
取り込まれる」、範囲計算を直した後は「全黒行の直後の数行がまるごと欠ける」に変わった。
原因はどちらも同じで、**送信側でヘッダの値の取り方が揃っていなかったこと**。

    row / ts / frame  送出開始時にFIFO先頭から直接スナップショット
    offset_px         先頭を毎サイクル追いかける2段レジスタ経由  ← これ

両者が同じFIFOエントリを指す保証がなく、範囲だけが fifo_depth ライン遅れて乗って
いた(depth 4→4ライン、8→8ライン の2点で確認)。内容のある行が空(count_px=0)で
送られるので行が欠け、範囲が隣の行のものになると絵が横にずれた。

修正は「範囲も row/ts と同じ瞬間に先頭からラッチし、派生値(断片数・長さ)は次の
サイクル(FSMの LPREP 状態)でそのラッチ値だけから作る」。同一エントリ由来が構造的に
保証される。実機で 525行すべて一致(`span_check` 100%、対照実験も100%)。

**この過程で否定された筋**(いずれも実測):
- DATACLKの位相/PLL/電源(VCOのsupply pushing)。LINEパケットの ts から offset_px を
  引いた隣接差が**全524箇所で htotal と一致**。HSOUTとDATACLKの関係は1行も動いて
  いない。**基板の設計変更は不要**
- メタFIFOの溢れ。動作中の `cap_drops` は0(購読していない間だけ溢れて溜まる)
- 面(face)の追い越し。`nface=16` にしても変化なし
- キャプチャの非黒判定。pixドメインで push 時点の値を見る窓(key 0x32)で内容と一致

**使った道具**(残してある):
- `key 0x30` 全ライン送信(Viewerのチェックボックス)。範囲判定を切って比較する。
  回避策としても有効で、31kHzで約555Mbps、GbEに収まる
- `key 0x31/0x32` 指定行の範囲を pix ドメインで直読、`0x33` cap_drops、
  `0x34` pop時のFIFO先頭の {row, x_lo, x_hi}
- `host/python/retrocastx/span_check.py` 範囲の一致率を測る(算術の自己検算つき)
- `host/python/retrocastx/line_probe.py` 生LINEパケットを行ごとに見る
- `gateware/sim_capture_black.py` 全黒行を挟んだときの範囲を検証

**測定で踏んだ落とし穴**(同じ形で3回止まった):
- `ts` は「ライン先頭」ではなく「ライン先頭 + offset_px」。差を htotal と比べると
  offset が動いた行が全部異常に見える
- entry 変換の式。末尾は `(offset + count - 1)//2`
- SIMの `hs_offset=0` は駆動側と1画素ずれる(RGBは1段・HSOUTは2段のレジスタ)。
  ずれを不具合と誤認した
- A/B比較の交絡。全ライン送信モードはFIFO滞留が違うので、通常モードと直接比べては
  いけない。同条件2回の自己一致率を先に出すこと

## 3. ライン長を超える断片が0.5%

各フィールドの特定位置(413行目付近と879行目付近)に集中する。HSYNCを取り逃がした行で
`x` が長く走り、非黒範囲がライン長を超えると考えている。受信側は入る分だけ書いて
凌いでいるが、ボード側で範囲をライン長で打ち切るのが本筋。

## 4. 管面の縦横比がCPU側とシェーダ側で食い違う

`tube_aspect = 0`(管面「そのまま」= 既定)のとき、両者が別の値を使う:

- CPU側(`main.rs` の CentralPanel): 切り出し範囲の比 `cw/ch`
- シェーダ側(`render.rs` の `uniforms`): 時間ベースかつ幾何が有効なら **4:3 固定**

描画callbackの矩形はCPU側の比で確保されるので、実際に映る管面はその中で
レターボックス/ピラーボックスされる。`画に合わせる` はCPU側の比でウィンドウを
決めるため、押しても管面はぴったり収まらない。

外側の色を撤去して黒に統一したので見た目には出ないが、比の計算が2か所にあること
自体が原因。本筋はシェーダに `avail` 全体を渡して管面の形をシェーダだけに決めさせ、
`画に合わせる` 用に描画サイズを返してもらうこと。

## 5. モニタプロファイル

`mon.15` / `mon.24` / `mon.31` に [H幅, H位置, V幅, V位置] を持つ。実CRTのつまみに
相当し、スライダーで合わせる。将来は CZ-600D / CZ-612D のような実在モニタの
プロファイルを外部ファイルにする案がある(オーバースキャン量、走査線の強さなど)。

信号は左右非対称(バックポーチが長い)なので `H位置 0` だと絵が右に寄る。
実測例: 15kHz Mode7 は `active 994x480 at (157,33)`, htotal 1179 → 適正な H位置は
(157 + 994/2)/1179 - 0.5 = +0.055。

## 参考: 現在の設計の要点

**幾何は同期信号だけで決まり、絵の内容に依存しない。**

```
水平位置 = (offset_px + k) / htotal      offset_px はライン内の絶対位置
垂直位置 = スロット / (slot_k × vtotal)   slot_k は mflags bit0 で伝える
```

**インターレースは設定ではなく測定で決まる。**

```
TVPの検出ビット(38h bit5)      インターレースかどうか
生VSYNCの半ライン位相          どちらのフィールドが下か(次のHSYNCまでが短い側が上)
TVP vtotal / 生ライン数の比    フィールド単位かフレーム単位か
```

**生同期(P4 pin155=HSYNC / pin153=VSYNC)は sysドメインで測る。** pll_divide に依存
しない絶対値が得られる(key 0x2A/0x2B/0x2C)。TVPのHSOUT/VSOUT経由の値は、TVPが
インターレースのVSYNCを間引くのでフレーム単位に畳まれている。

**pll_divide はドットクロック再生専用で、描画位置に影響しない。** hs_offset は
設定項目から撤去済み(既定0)。
