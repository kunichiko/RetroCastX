# RetroCastX 伝送プロトコル v0(ドラフト)

RFC 4175(RTP Payload Format for Uncompressed Video)の「ライン単位パケット化 + ピクセルオフセット」
の考え方を下敷きにした、UDP 上の独自軽量プロトコル。将来 RTP でラップして標準ツールと接続する余地を残す。

- トランスポート: UDP / IPv4。デフォルトポート **34600**
- バイトオーダー: **リトルエンディアン**(FPGA・x86/ARM 双方で自然なため)
- 再送なし。パケットロスは受信側が前フレームのラインで補完(シーケンス番号で検出のみ行う)
- 1パケット = 1ライン(または MTU 超過時はラインの断片)。標準MTU(1500)とジャンボフレーム両対応

## 共通ヘッダ(8 bytes)

| offset | size | field | 説明 |
|---|---|---|---|
| 0 | u8 | magic | `0x52` ('R') |
| 1 | u8 | version | `0x00` |
| 2 | u8 | type | 0=LINE, 1=MODE, 2=AUDIO, 3=INFO, 4=SUBSCRIBE, 5=CONFIG |
| 3 | u8 | flags | type 依存(下記) |
| 4 | u16 | frame | フレームカウンタ(VSYNC ごとに +1、ラップあり) |
| 6 | u16 | seq | 全パケット共通のシーケンス番号(ロス検出用、ラップあり) |

## LINE パケット(type=0)

共通ヘッダに続き 12 bytes のラインヘッダ、その後ピクセルデータ。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | u16 | line | フレーム内ライン番号(0 = アクティブ領域先頭) |
| 10 | u16 | offset_px | この断片の先頭ピクセルの、ライン内オフセット(断片化時以外 0) |
| 12 | u16 | count_px | この断片に含まれるピクセル数 |
| 14 | u8 | pixfmt | 0=RGB888(3B/px), 1=RGB555(2B/px), 2=RGB565(2B/px), 3=YC8(2B/px) |
| 15 | u8 | mode_id | 現在有効な MODE 記述子の ID(タイミング変更検出用) |
| 16 | u32 | timestamp | この断片の先頭ピクセルサンプル時点のドットクロックカウンタ値 |

flags: bit0 = LAST_FRAGMENT(このパケットでラインが完結)、bit1 = FIELD_ODD(インターレース奇数フィールド)

- `timestamp` は FPGA 内でピクセルクロックをフリーランカウント(32bit、ラップあり)した値。
  受信側はこれで HSYNC/VSYNC タイミング(ライン間隔・フレーム間隔)を再構成できる。
- ラインが MTU に収まらない場合は `offset_px` を進めて複数パケットに分割(RFC 4175 と同じ発想)。
  例: 768px × RGB888 = 2304B → 標準MTUでは 2 断片。ジャンボフレーム(MTU 9000)なら常に 1 断片。

### pixfmt = 3 (YC8)

**復調していない生のADC値**を運ぶための形式。2B/px で、

| byte | 内容 |
|---|---|
| 0 | 緑チャネル 8bit。コンポジットなら **CVBS そのもの**、S-Video なら **Y** |
| 1 | 赤チャネル 8bit。S-Video の **C**(コンポジット運用では未接続なので≒0) |

- **2B/px は RGB555 と同じ**なので、断片化・MTU計算・受信側のバッファ確保は共通。
  1B/px の専用形式にすれば帯域は半分になるが、詰め方が全部別系統になる。
- 色副搬送波の位相を推定するには 8bit が必要。RGB555 の 5bit ではカラーバーストが
  9コード p-p しか無く精度が足りない(詳細は `composite-video-plan.md` §3)。
- **この形式では「黒でない範囲」の最適化は成立しない。** ブランキングもカラーバーストも
  ライン全体が中身なので、ボードは常に 1ライン = htotal 画素を送る
  (CONFIG key 0x36 を 3 にすると key 0x30 相当が自動で有効になる)。
- 受信側の既定の見せ方は **Y をグレースケールに置くだけ**。1ラインの波形
  (同期チップ→ブリーズウェイ→カラーバースト→映像)がそのまま絵になるので、
  クランプとゲインが合っているかを目で確認できる。復調は別レイヤの仕事。

### インターレース(MODE mflags bit0=1)の規約

X68000 の 15kHz 512×512 系などのインターレースモード用。**受信側の再構成コードは
プログレッシブと共通**になるよう、座標系はフルフレームで統一する:

- MODE の `vactive` は**フルフレームの行数**(両フィールド合計)、`vtotal` も同様
- 共通ヘッダの `frame` は**フィールドごとに +1**(フィールド=伝送単位のフレーム)
- LINE の `line` は**フルフレーム座標の行番号**。ゲートウェアが
  `2×フィールド内行 + フィールド極性` を計算して付与する
- 奇数フィールドの LINE は flags bit1(FIELD_ODD)を立てる(受信側での
  bob 表示やフィールド極性の統計用。weave 合成だけなら参照不要)
- 受信側はフィールドを受けるたびに半分の行だけ更新されたフレームを得る
  (fill_ratio ≈ 0.5 が正常値)。前フィールドの行が残るため**自然に weave 合成**になる
- **bob 表示**(フィールドを縦2倍して フィールドレートで表示。動きが滑らかで
  コーミングなし)は受信側の表示オプションとして実装(FIELD_ODD で半行オフセット)

## MODE パケット(type=1)

タイミング記述子。**変更時に即時送出**し、以後も毎秒 1 回程度再送(途中参加の受信器のため)。
`mode_id` をインクリメントすることで、受信側は LINE ヘッダの `mode_id` 不一致から
「新しい MODE をまだ受けていない」ことを検出できる。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | u8 | mode_id | 記述子 ID(変更ごとに +1、ラップあり) |
| 9 | u8 | pixfmt | 以後の LINE の既定ピクセル形式 |
| 10 | u16 | mflags | bit0=interlace, bit1=hsync 極性(1=負), bit2=vsync 極性 |
| 12 | u16 | hactive | 水平有効ピクセル数 |
| 14 | u16 | htotal | 水平トータル(ドットクロック数) |
| 16 | u16 | vactive | 垂直有効ライン数 |
| 18 | u16 | vtotal | 垂直トータルライン数 |
| 20 | u32 | dotclk_hz | 再生ドットクロック周波数 [Hz](FPGA で実測) |
| 24 | u32 | hfreq_mhz_x1000 | 水平周波数 [mHz](=Hz×1000、実測) |
| 28 | u32 | vfreq_mhz_x1000 | 垂直周波数 [mHz](=Hz×1000、実測) |

## AUDIO パケット(type=2)

音声サンプル。入力は3系統あり(基板仕様)、**複数系統の同時転送も可**
(パケットごとに `source` が付くため受信側で分離できる)。どの系統を送るかは
CONFIG(key 0x0001)で選択する。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | u8 | source | 0=RGB端子(D-SUB15)音声, 1=LINE入力, 2=S/PDIF |
| 9 | u8 | format | 0=PCM s16le 2ch(L/Rインターリーブ) |
| 10 | u16 | nsamples | このパケットのサンプルフレーム数(L+Rで1) |
| 12 | u32 | rate_hz | 実サンプルレート(アナログ=48000、S/PDIFは受信ストリームの実測) |
| 16 | u32 | timestamp | 先頭サンプル取得時点の**ドットクロックカウンタ**(LINEと同一カウンタ → A/V同期はこれで取る) |
| 20 | ... | samples | L0 R0 L1 R1 ... (s16le) |

- 目安: 48kHz で 240サンプル/パケット(5ms) → 980B、200pkt/s、~1.6Mbps/系統
- flags: 予約(0)
- S/PDIFの44.1kHz等は `rate_hz` で通知(受信側でリサンプルするか、そのまま再生)

## CONFIG パケット(type=5)

アプリ→ボードの設定読み書き。ボードは同レイアウトに flags bit0(REPLY)を立て、
`value` に現在値(SET後は反映値)を入れてユニキャスト返信する。応答が来なければ
アプリが再送する(冪等)。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | 6B | mac | 宛先ボードMAC(全FF=ワイルドカード)。応答時は**ボード自身のMAC** |
| 14 | 2B | reserved | 0 |
| 16 | u8 | target | 0=キャプチャボード, 1=ArgusX(RGBセレクタ、I2C経由) |
| 17 | u8 | op | 0=SET, 1=GET |
| 18 | u16 | key | 下表 |
| 20 | u32 | value | SET時の設定値 / 応答時の現在値 |

- SUBSCRIBEと同じMAC照合を行い、一致またはワイルドカードのときのみ反応する。
  応答の mac にはボード自身のMACが入るため、静的IP衝突環境でも応答元を判別できる

キー(ドラフト):

| target | key | 意味 |
|---|---|---|
| 0 (board) | 0x0001 | audio_enable_mask: bit0=RGB端子音声, bit1=LINE, bit2=S/PDIF |
| 0 (board) | 0x0002 | spdif_rate_hz: S/PDIFの実測サンプルレート[Hz]。**読み取り専用**。0 ならデコーダがサンプルを出していない |
| 0 (board) | 0x0003 | spdif_fifo_level: S/PDIF送出FIFOの滞留サンプル数。**読み取り専用**。レートが出ているのにここが0なら詰まりは後段 |
| 1 (ArgusX) | 0x0001 | 映像入力選択(値の意味はArgusX側仕様で定義) |
| 0 (board) | 0x0022 | sync_ctl (TVP reg 0Eh): 0x52=5線 / 0x53=4線TTL C-SYNC / 0x5B=SOG |
| 0 (board) | 0x0050 | sog_thresh (TVP reg 10h): SOGスライス閾値 |
| 0 (board) | 0x0051 | sep_thresh (TVP reg 11h): 同期セパレータ閾値 |
| 0 (board) | 0x0052 | precoast (TVP reg 12h): プリコースト[ライン]。最低1が必要 |
| 0 (board) | 0x0053 | postcoast (TVP reg 13h): ポストコースト[ライン]。最低1が必要 |
| 0 (board) | 0x0054 | syncdet (TVP reg 14h): 同期検出ステータス。**読み取り専用** |
| 0 (board) | 0x0055 | lines_per_frame (TVP reg 37h:38h): TVPが測ったライン数/フレーム。**読み取り専用** |
| 0 (board) | 0x0056 | clocks_per_line (TVP reg 39h:3Ah): TVPが測ったDATACLK数/ライン。**読み取り専用** |

- 0x0054〜0x0056 は **TVP自身の測定値**で、ボードのキャプチャロジックに依存しない。
  SOG(映像レベルC-SYNC)運用では生同期ピンが無信号になり 0x002A〜0x002C が使えないため、
  「H/Vが入力にロックしているか」を判定できる唯一の絶対測定になる
- 0x0050 は 5bit値。TVP reg 10h の下位3bitはクランプ選択で共用されているので、
  **閾値(0x0050)とクランプ選択(0x005E)を別キーで持ち、書き込み時に連結する**。
  1本のキーで生の8bitを書くと、片方を触るともう片方を巻き込んで壊れる

### 映像入力の方式切り替え用のキー

| target | key | 説明 |
|---|---|---|
| 0 (board) | 0x0036 | pixfmt: 伝送ピクセル形式。0=RGB888 / 1=RGB555(既定) / 3=YC8(生8bit) |
| 0 (board) | 0x0037 | black_th: 非黒判定の閾値(成分の上位5bit と比較, 0..31)。既定0。**上げると暗い絵の中身が範囲から外れて送られなくなる** |
| 0 (board) | 0x005E | clamp_sel (TVP reg 10h[2:0]): bit2=Blue bit1=Green bit0=Red。0=ボトム 1=ミッド |
| 0 (board) | 0x005F | coarse_gain_gb (TVP reg 1Bh): **[7:4]=Green [3:0]=Blue**。Gain = 0.5 + N/10 |
| 0 (board) | 0x0065 | coarse_off_g (TVP reg 1Fh[5:0]): 粗アナログオフセット Green。10h=+64コード |
| 0 (board) | 0x0067 | coarse_gain_r (TVP reg 1Ch): **[7:4]=Reserved [3:0]=Red**。1Bhとビット割りが違う |
| 0 (board) | 0x0068 | coarse_off_r (TVP reg 20h[5:0]): 粗アナログオフセット Red |
| 0 (board) | 0x0069 | in_mux1 (TVP reg 19h): [7:6]=SOG [5:4]=R [3:2]=G [1:0]=B、00=_1/01=_2/10=_3 |

**0x005E と 0x005F は必ずセットで動かす。** ミッドレベルクランプにするとブランキングが
コード512に座るので、白側(+100 IRE)に使えるヘッドルームが半分になる。既定の粗ゲイン
1.2倍のままではコンポジット(1Vpp=140 IRE)が飽和する(データシート 1Bh は
「Vpp × Gain < 1Vpp」を要求する)。数値の内訳は `composite-video-plan.md` §2。

**0x005F と 0x0067 は同じ「1.2倍」でも値が違う**(1Bh=0x77 / 1Ch=0x07)。
1Bh は Blue と Green の2チャネルぶんを1バイトに詰めているため。

**0x0069 は入力方式の切り替えに必須。** 以前はビルド時定数だったので、SOG の入力ピンが
違う機種(MSXのC-SYNCは SOGIN_2)に切り替えるにはビットストリームの焼き直しが要った。
なお **HSYNC_A/_B・VSYNC_A/_B の選択は 19h ではなく 1Ah bit0/bit2**(key 0x005D)。

- 0x0010〜0x002C・0x0030〜0x0036・0x0040〜0x0045 は画枠パラメータと診断用の
  読み出しに割り当て済み。**新しい設定キーは 0x0050 以降から取る**
  (0x0023〜0x0026 は診断キーと衝突する)
- **0x0013〜0x0016 は空いていない。** インターレース判定が「設定」から「測定」へ
  移ったのでゲートウェアは読まなくなったが、`CFG_KEY_INTERLACE` などの名前が
  host/client に残っているので再利用してはいけない。
  現時点で真に空いているのは 0x002D〜0x002F / 0x0038〜0x003F / 0x0046〜0x004F /
  0x006A 以降

キーの割り当ては `host/python/retrocastx/protocol.py` の `CFG_KEY_*` を正とし、
ゲートウェア側は `gateware/retrocastx_stream.py` の `reply_cases` と対応させる。

- ArgusX宛のCONFIGは、ゲートウェアがI2Cバス(TVP7002と共有、J11コネクタ)経由で
  ArgusXへ中継する。ArgusXのI2Cアドレス・レジスタマップはArgusX側で確定後に反映
- 認証なし(同一LAN前提)。SETは全て冪等な値設定のみとする
- **ブロードキャスト可**(SUBSCRIBEと同様)。PCとボードのサブネットが食い違う構成
  (直結・DHCPなし等)ではユニキャストがOSのルーティングで送れないため、
  アプリはCONFIGもブロードキャストで送ってよい。ただし同一LANの全ボードに
  適用されるため、複数ボード環境ではDHCP導入後にユニキャストで送ること
- ブロードキャストで送る場合、**アプリは応答の flags bit0(REPLY)を必ず検査する**。
  ブロードキャストは自分自身の送信パケットにもループバックするため、REPLYを見ないと
  自分の要求を応答と誤認し、SETが常に成功・GETが常に送った値に見える(実際に踏んだ)

## INFO / ANNOUNCE パケット(type=3)

ボードの自己紹介。**発見(Discovery)と生存確認**に使う。共通ヘッダに続き 32 bytes:

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | 6B | mac | ボードのMACアドレス |
| 14 | 4B | ip | ボードが自認するIPv4(参考値。**受信側はUDP送信元アドレスを正とする**) |
| 18 | u16 | udp_port | データ/制御ポート |
| 20 | u16 | fw_version | ファームウェアバージョン |
| 22 | u16 | caps | 能力ビット(bit0=TVP7002, bit1=アナログ音声, bit2=S/PDIF, bit3=ArgusX接続) |
| 24 | 16B | name | ASCII名(NUL詰め) |

## SUBSCRIBE パケット(type=4)

アプリ→ボード。共通ヘッダに続き 8 bytes。**ブロードキャスト可**。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | 6B | mac | 宛先ボードのMAC。全FF(`ff:ff:ff:ff:ff:ff`)=ワイルドカード(全ボード) |
| 14 | 2B | reserved | 0 |

- ボードは **mac が自分のMACと一致、またはワイルドカード** のときのみ反応する。
  一致しなければ完全に無視(応答もストリーム切替もしない)
- flags bit0 = ANNOUNCE_ONLY: 1なら発見のみ(ボードはANNOUNCEを送信元へユニキャスト返信)
- flags bit0 = 0 なら、ボードは以後の映像ストリームの送り先を**このパケットの送信元**に切り替え、
  ANNOUNCEを返す。購読は最後のSUBSCRIBEから10秒で失効(アプリは定期再送する)
- **複数ボード運用**: ワイルドカードでの本購読(ANNOUNCE_ONLY=0)は全ボードが同時に
  ストリームを向けてくるため単一ボードLAN専用。複数ボード環境では
  ①ワイルドカード+ANNOUNCE_ONLY で発見 → ②ANNOUNCE で各ボードのMACを取得 →
  ③目的ボードのMACを指名して本購読、とする(ブロードキャスト送信のままでよい)

## アドレッシングと発見の設計

- **MACアドレス**: 基板のEUI-48 EEPROM(24AA025E48、ポートごとに1個)から
  起動時に読み出したグローバル一意アドレスを使用。EEPROM未実装/読出し失敗時は
  ローカル管理アドレス `02:52:43:58:xx:xx`("RCX"、既定 `02:52:43:58:00:01`)に
  フォールバック
- **発見はアプリ起点**: アプリが `255.255.255.255:34600` へ SUBSCRIBE(ANNOUNCE_ONLY) を
  ブロードキャスト → ボードがユニキャストで ANNOUNCE 返信。
  ボード側受信はブロードキャスト対応(LiteEth `with_broadcast=True`)なので、
  **ボードとPCのサブネット設定が食い違っていても同一L2セグメントなら発見できる**
- **IPアドレス**: 既定は静的(192.168.10.50)。DHCPは LiteEth 同梱のハードウェア
  DHCPクライアント(`liteeth/core/dhcp.py`)でフェーズ2に導入予定(取得失敗時は
  静的値にフォールバック)。**リンクローカル(RFC 3927 AutoIP)はボード側には実装しない**:
  アプリ→ボードは全てブロードキャスト可、ボード→アプリは宛先を直接解決する
  (ゲートウェイ概念なし=全てオンリンク扱い)ため、DHCPサーバの無い直結構成
  (PC側が169.254.x.x自己割当)でもサブネット不一致のまま全通信が成立する。
  ただし**ARPで引くだけでは足りない**: Windows は別サブネットの送信元から来た
  ARP要求に応答しない(strong host model)。そのためボードは**受信パケットから
  相手のMACを学習**して返す(`gateware/retrocastx_net.py`、design-notes 参照)
- 映像の送り先はSUBSCRIBE送信元に動的に決まるため、アプリ側のIP設定は不要

## 帯域の目安

| モード | アクティブレート | RGB888 | RGB555 |
|---|---|---|---|
| 768×512@55.46(X68000 31kHz) | ~24 Mpx/s | ~580 Mbps | ~390 Mbps |
| 640×400@56.4(PC-98 24kHz) | ~14 Mpx/s | ~350 Mbps | ~230 Mbps |
| 512×512@55.46(X68000 15kHz) | ~8 Mpx/s | ~190 Mbps | ~130 Mbps |

ヘッダオーバーヘッドは 20B/ライン + UDP/IP/Ether 42B ≒ ライン当たり 62B(2304B に対し 2.7%)。

## 受信側の再構成方針

1. MODE を受けてフレームバッファ(hactive×vactive)を確保
2. LINE を `frame`/`line`/`offset_px` に従って書き込み
3. VSYNC 相当は「`frame` が進んだこと」で検出(将来: FRAME_END フラグの追加を検討)
4. 表示は 2 通り:
   - **フレーム同期モード**: フレーム完成を待って表示(実装が簡単、遅延 ≦1フレーム)
   - **レースザビームモード**: 受信したラインから逐次テクスチャ更新(最小遅延、VRR 前提)
5. パレット吸着(オプション): 機種プロファイル(例: X68000 = RGB 5bit)に基づき
   受信 8bit 値を最近傍のネイティブパレット値にスナップ
