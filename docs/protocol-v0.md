# RetroCastX 伝送プロトコル v0(ドラフト)

RFC 4175(RTP Payload Format for Uncompressed Video)の「ライン単位パケット化 + ピクセルオフセット」
の考え方を下敷きにした、UDP 上の独自軽量プロトコル。将来 RTP でラップして標準ツールと接続する余地を残す。

- トランスポート: UDP / IPv4。デフォルトポート **34600**
- バイトオーダー: **リトルエンディアン**(FPGA・x86/ARM 双方で自然なため)
- 再送なし。パケットロスは受信側が前フレームのラインで補完(シーケンス番号で検出のみ行う)
- 1パケット = 1ライン(または MTU 超過時はラインの断片)。標準MTU(1500)とジャンボフレーム両対応

## 共通ヘッダ(8 bytes)

| offset | size | field | 説明 |
|---|---|---|---|
| 0 | u8 | magic | `0x52` ('R') |
| 1 | u8 | version | `0x00` |
| 2 | u8 | type | 0=LINE, 1=MODE, 2=AUDIO, 3=INFO, 4=SUBSCRIBE, 5=CONFIG |
| 3 | u8 | flags | type 依存(下記) |
| 4 | u16 | frame | フレームカウンタ(VSYNC ごとに +1、ラップあり) |
| 6 | u16 | seq | 全パケット共通のシーケンス番号(ロス検出用、ラップあり) |

## LINE パケット(type=0)

共通ヘッダに続き 12 bytes のラインヘッダ、その後ピクセルデータ。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | u16 | line | フレーム内ライン番号(0 = アクティブ領域先頭) |
| 10 | u16 | offset_px | この断片の先頭ピクセルの、ライン内オフセット(断片化時以外 0) |
| 12 | u16 | count_px | この断片に含まれるピクセル数 |
| 14 | u8 | pixfmt | 0=RGB888(3B/px), 1=RGB555(2B/px), 2=RGB565(2B/px), 3=YC8(2B/px), 4=YCC422(2B/px), 5=CVBS8(1B/px) |
| 15 | u8 | mode_id | 現在有効な MODE 記述子の ID(タイミング変更検出用) |
| 16 | u32 | timestamp | この断片の先頭ピクセルサンプル時点のドットクロックカウンタ値 |

flags: bit0 = LAST_FRAGMENT(このパケットでラインが完結)、bit1 = FIELD_ODD(インターレース奇数フィールド)

- `timestamp` は FPGA 内でピクセルクロックをフリーランカウント(32bit、ラップあり)した値。
  受信側はこれで HSYNC/VSYNC タイミング(ライン間隔・フレーム間隔)を再構成できる。
- ラインが MTU に収まらない場合は `offset_px` を進めて複数パケットに分割(RFC 4175 と同じ発想)。
  例: 768px × RGB888 = 2304B → 標準MTUでは 2 断片。ジャンボフレーム(MTU 9000)なら常に 1 断片。

### pixfmt = 3 (YC8)

**復調していない生のADC値**を運ぶための形式。2B/px で、

| byte | 内容 |
|---|---|
| 0 | 緑チャネル 8bit。コンポジットなら **CVBS そのもの**、S-Video なら **Y** |
| 1 | 赤チャネル 8bit。S-Video の **C**(コンポジット運用では未接続なので≒0) |

- **2B/px は RGB555 と同じ**なので、断片化・MTU計算・受信側のバッファ確保は共通。
  1B/px の専用形式にすれば帯域は半分になるが、詰め方が全部別系統になる。
- 色副搬送波の位相を推定するには 8bit が必要。RGB555 の 5bit ではカラーバーストが
  9コード p-p しか無く精度が足りない(詳細は `composite-video-plan.md` §3)。
- **この形式では「黒でない範囲」の最適化は成立しない。** ブランキングもカラーバーストも
  ライン全体が中身なので、ボードは常に 1ライン = htotal 画素を送る
  (CONFIG key 0x36 を 3 にすると key 0x30 相当が自動で有効になる)。
- 受信側の既定の見せ方は **Y をグレースケールに置くだけ**。1ラインの波形
  (同期チップ→ブリーズウェイ→カラーバースト→映像)がそのまま絵になるので、
  クランプとゲインが合っているかを目で確認できる。復調は別レイヤの仕事。

### インターレース(MODE mflags bit0=1)の規約

X68000 の 15kHz 512×512 系などのインターレースモード用。**受信側の再構成コードは
プログレッシブと共通**になるよう、座標系はフルフレームで統一する:

- MODE の `vactive` は**フルフレームの行数**(両フィールド合計)、`vtotal` も同様
- 共通ヘッダの `frame` は**フィールドごとに +1**(フィールド=伝送単位のフレーム)
- LINE の `line` は**フルフレーム座標の行番号**。ゲートウェアが
  `2×フィールド内行 + フィールド極性` を計算して付与する
- 奇数フィールドの LINE は flags bit1(FIELD_ODD)を立てる(受信側での
  bob 表示やフィールド極性の統計用。weave 合成だけなら参照不要)
- 受信側はフィールドを受けるたびに半分の行だけ更新されたフレームを得る
  (fill_ratio ≈ 0.5 が正常値)。前フィールドの行が残るため**自然に weave 合成**になる
- **bob 表示**(フィールドを縦2倍して フィールドレートで表示。動きが滑らかで
  コーミングなし)は受信側の表示オプションとして実装(FIELD_ODD で半行オフセット)

## MODE パケット(type=1)

タイミング記述子。**変更時に即時送出**し、以後も毎秒 1 回程度再送(途中参加の受信器のため)。
実機のゲートウェア(gw-v1.5.0 以降)が「変更時」に送るのは、次のいずれかのとき:

- 1フレームの組(下の末尾)が新しいモードの値になった(切り替わりから3〜4フレーム)
- `vactive`(vtotal の追従を待つので、組より数フレーム遅れる)
- `htotal`(TVP に書いた pll_divide)
`mode_id` をインクリメントすることで、受信側は LINE ヘッダの `mode_id` 不一致から
「新しい MODE をまだ受けていない」ことを検出できる。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | u8 | mode_id | 記述子 ID(変更ごとに +1、ラップあり) |
| 9 | u8 | pixfmt | 以後の LINE の既定ピクセル形式 |
| 10 | u16 | mflags | bit0=interlace, bit1=hsync 極性(1=負), bit2=vsync 極性 |
| 12 | u16 | hactive | 水平有効ピクセル数 |
| 14 | u16 | htotal | 水平トータル(ドットクロック数) |
| 16 | u16 | vactive | 垂直有効ライン数 |
| 18 | u16 | vtotal | 垂直トータルライン数 |
| 20 | u32 | dotclk_hz | 再生ドットクロック周波数 [Hz](FPGA で実測) |
| 24 | u32 | hfreq_mhz_x1000 | 水平周波数 [mHz](=Hz×1000、実測) |
| 28 | u32 | vfreq_mhz_x1000 | 垂直周波数 [mHz](=Hz×1000、実測) |
| 32 | u32 | frame_clocks | 直近 `frame_vsyncs` 回の VSYNC 間の長さの合計 [sys クロック数]。0 = 測れていない(caps bit3) |
| 36 | u16 | frame_lines | 同じ区間の HSYNC 数(caps bit3) |
| 38 | u16 | frame_vsyncs | 上の2つが何回分の VSYNC 間か(実機は 2。0 は 1 とみなす) |
| 40 | u32 | sys_clk_hz | ボードの sys クロック周波数 [Hz](caps bit3) |

末尾の 12 バイト(offset 32〜43)は caps bit3 のボードだけが付ける。古い受信側は読まずに
無視する(MODE は 32 バイト以上ならよい)。

★**fH・fV は末尾の組から出すこと。** `fV = sys_clk_hz × frame_vsyncs / frame_clocks`、
`fH = sys_clk_hz × frame_lines / frame_clocks`。2回分を合計するのは、インターレース
(1フィールド 260.5 ライン)で VSYNC 間の HSYNC 数が 260/261 と交互になり、1回分だと
fH が ±0.2% 揺れるため。`hfreq`/`vfreq`/`dotclk` の欄は1秒窓(fV は8秒積算)で測った値で、
モードを切り替えた直後は前後が混ざった値(15.98kHz と 31.5kHz の間の約24kHz)や、
`vtotal` だけ新しく fH は古い値を持つ(2026-11-10 実機)。組は同じフレームから取るので
必ず合い、精度も1フレームで 1〜2ppm(1秒窓の ±1Hz は 32〜63ppm)。
同じ組が3フレーム続いたときだけ更新するので、偽VSYNCで割れたフレームは通らない。
`frame_clocks` が 0(VSYNC が約1.5秒来ない)のときは1秒窓の欄に戻る。

★**htotal は TVP に書いている pll_divide**(gw-v1.5.0 以降)。以前は1秒窓で測った値で、
PLL を書き換えてから最大1秒古く、受信側がフレームの幅と横位置を誤った。PLL がロック
していれば DATACLK ÷ HSYNC は分周比そのものなので、書いた値が正しい。

★**キャプチャ版のゲートウェアでは hactive / vactive は「有効映像の大きさ」ではない。**

- `hactive` はラインバッファの幅(ビルド時の定数 `width`、いまは **2048**)。
  ラインの頭(hs_offset=0)からブランキングごと取り込み、中身のある範囲だけを
  送るので、全モードの htotal(15kHz 1216 / 24kHz 1408 / 31kHz 1104 / NTSC 8fsc 1820)
  が入る幅にしてある。実際の1ラインのサンプル数は `htotal`
- `vactive` は**半ライン単位のスロット数**(インターレースの第2フィールドを半ライン
  ずれた位置に置くため)で、`(vtotal − vbp) × 2`。NTSC なら 263 × 2 = 526
- 有効映像の位置と大きさは受信側が絵から実測する(Viewer の act_x/act_y/act_w/act_h)

### ANNOUNCE の fw_version と caps

`fw_version` は `gw-vX.Y.Z` タグから作る **u16** で、
`bit15:12=major(0〜15) bit11:6=minor(0〜63) bit5:0=patch(0〜63)`。
タグが無いビルドは `0x0000`。

★**16進の桁に揃えるより範囲を優先している。** 4/4/8 なら 0.9.2 が `0x0902` と
そのまま読めるが、パッチが15で頭打ちになる(gw-v0.9.0〜0.9.2 を2日で3つ出した
実績があり、活発な時期には溢れる)。表示側が復号して "0.9.2" と出すので、
人が16進のまま読む場面は無い。
**中身まで一意に指したいときは CONFIG key 0x09(ビルド元コミットのSHA)を読む。**

`caps` の **bit0 = MACを基板のEEPROMから読めた**。0 なら全基板共通のフォールバック
アドレスで動いているので、**同じLANに2枚繋ぐと衝突する**。出荷検査で弾くこと。

`caps` の **bit2 = CAP_LED_IDLE**: 小亀のLEDの切断中の動作(CONFIG 0x0097)に対応している。

`caps` の **bit3 = CAP_FRAME_CLOCKS**: MODE の末尾に1フレームの組(`frame_clocks`・
`frame_lines`・`sys_clk_hz`)が付き、`htotal` は書いた pll_divide(gw-v1.5.0 以降)。
組から出した fH は前後のモードが混ざらないので、受信側は届いたライン数と合う MODE を
1回で信用してよい(無ければ同じ帯域が2回続くのを待つ)。

`caps` の **bit1 = CAP_COMPACT**: 帯域を減らす伝送形式(pixfmt 4=YCC422 / 5=CVBS8)、
送出範囲の固定(CONFIG 0x0038/0x0039)、間引きの対モード(0x0035 bit4)に対応している。
**古いゲートウェアに 4・5 を書くと RGB555 の詰め方で送られて絵が壊れる**ので、
受信側はこのビットを見てから使う。

## 帯域を減らす伝送形式

1ラインが何パケットに分かれるかで、受信側の負担(1秒あたりのパケット数)が決まる。
標準MTUで1パケットに入る画素数は、2B/px で 724、1B/px で 1452。

- **YCC422(4、2B/px)**: コンポーネント用。2画素で `Y0 Cb0 Y1 Cr0`(色差は偶数画素の
  値)。チャネルの割り当ては R=Pr / G=Y / B=Pb。RGB888 の 2/3 で、8bit のまま運ぶので
  RGB555 のような階調の段差が出ない
- **CVBS8(5、1B/px)**: コンポジット用。緑ch(CVBS)だけを1バイトずつ。YC8 の赤ch
  (S端子の C)はコンポジットでは未接続でほぼ0なので、捨てても絵は変わらない。
  8fsc の1ライン 1820 サンプルが3パケットから2パケットに減る。YC8 と同じく
  ライン全体(バーストを含む)を送る
- **送出範囲の固定(0x0038/0x0039)**: コンポーネントは色差の無信号が中間値で
  「黒」にならず、「黒でない範囲」の判定がライン全体に広がる。Viewer は
  `[112, 836)` を送らせ、バックポーチの終わり8サンプル(黒の基準)と有効画素を
  1パケット(YCC422 で 724画素)に収める。480i で毎秒 約31,500 → 約15,700 パケット

## AUDIO パケット(type=2)

音声サンプル。入力は4系統あり(v1.0 基板。アナログ3 + S/PDIF)、**複数系統の同時転送も可**
(パケットごとに `source` が付くため受信側で分離できる)。どの系統を送るかは
CONFIG(key 0x0001)で選択する。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | u8 | source | 0=RGB端子(D-SUB15)音声, 1=MSX(ミニDIN8)音声, 2=S/PDIF, 3=コンポジット(小亀基板)音声 |
| 9 | u8 | format | 0=PCM s16le 2ch(L/Rインターリーブ) |
| 10 | u16 | nsamples | このパケットのサンプルフレーム数(L+Rで1) |
| 12 | u32 | rate_hz | 実サンプルレート(アナログ=48000、S/PDIFは受信ストリームの実測) |
| 16 | u32 | timestamp | 先頭サンプル取得時点の**ドットクロックカウンタ**(LINEと同一カウンタ → A/V同期はこれで取る) |
| 20 | ... | samples | L0 R0 L1 R1 ... (s16le) |

- 目安: 48kHz で 240サンプル/パケット(5ms) → 980B、200pkt/s、~1.6Mbps/系統
- flags: 予約(0)
- S/PDIFの44.1kHz等は `rate_hz` で通知(受信側でリサンプルするか、そのまま再生)
- v0.9.0 基板では 1=基板上のLINE入力で、3 は無かった。v1.0 で LINE 入力を廃して
  映像系統ごとのADCにしたとき、S/PDIF の 2 を動かさないよう**コンポジットを末尾の3に足した**

## CONFIG パケット(type=5)

アプリ→ボードの設定読み書き。ボードは同レイアウトに flags bit0(REPLY)を立て、
`value` に現在値(SET後は反映値)を入れてユニキャスト返信する。応答が来なければ
アプリが再送する(冪等)。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | 6B | mac | 宛先ボードMAC(全FF=ワイルドカード)。応答時は**ボード自身のMAC** |
| 14 | 2B | reserved | 0 |
| 16 | u8 | target | 0=キャプチャボード, 1=ArgusX(RGBセレクタ、I2C経由) |
| 17 | u8 | op | 0=SET, 1=GET |
| 18 | u16 | key | 下表 |
| 20 | u32 | value | SET時の設定値 / 応答時の現在値 |

- SUBSCRIBEと同じMAC照合を行い、一致またはワイルドカードのときのみ反応する。
  応答の mac にはボード自身のMACが入るため、静的IP衝突環境でも応答元を判別できる

キー(ドラフト):

| target | key | 意味 |
|---|---|---|
| 0 (board) | 0x0001 | audio_enable_mask: bit0=RGB端子音声, bit1=MSX, bit2=S/PDIF, bit3=コンポジット。既定 0b1111 |
| 0 (board) | 0x0002 | spdif_rate_hz: S/PDIFの実測サンプルレート[Hz]。**読み取り専用**。0 ならデコーダがサンプルを出していない |

| 0 (board) | 0x0005 | spdif_resyncs: デコーダを立て直した回数。**読み取り専用**。増えていれば上記の状態に落ちて自動復帰している |

| 0 (board) | 0x0050 | sog_thresh (TVP reg 10h): SOGスライス閾値 |
| 0 (board) | 0x0051 | sep_thresh (TVP reg 11h): 同期セパレータ閾値 |
| 0 (board) | 0x0052 | precoast (TVP reg 12h): プリコースト[ライン]。最低1が必要 |
| 0 (board) | 0x0053 | postcoast (TVP reg 13h): ポストコースト[ライン]。最低1が必要 |
| 0 (board) | 0x0054 | syncdet (TVP reg 14h): 同期検出ステータス。**読み取り専用** |
| 0 (board) | 0x0055 | lines_per_frame (TVP reg 37h:38h): TVPが測ったライン数/フレーム。**読み取り専用** |

  「H/Vが入力にロックしているか」を判定できる唯一の絶対測定になる
- 0x0050 は 5bit値。TVP reg 10h の下位3bitはクランプ選択で共用されているので、
  **閾値(0x0050)とクランプ選択(0x005E)を別キーで持ち、書き込み時に連結する**。
  1本のキーで生の8bitを書くと、片方を触るともう片方を巻き込んで壊れる

### 映像入力の方式切り替え用のキー

| target | key | 説明 |
|---|---|---|
| 0 (board) | 0x0035 | frame_skip: bit3:0 = 間引き数 N(0=毎フレーム、1=2回に1回…)。bit4 = 対モード(下記)。映像(LINE)だけを間引き、音声は間引かない |
| 0 (board) | 0x0036 | pixfmt: 伝送ピクセル形式。0=RGB888 / 1=RGB555(既定) / 3=YC8(生8bit) / 4=YCC422 / 5=CVBS8(4・5 は caps bit1 が要る) |
| 0 (board) | 0x0038 | win_start: 送出範囲の固定の開始画素(caps bit1 が要る) |
| 0 (board) | 0x0039 | win_len: 送出範囲の固定の画素数。0 なら従来の「黒でない範囲」の自動判定。YC8 / CVBS8 / 全ライン送信(0x0030)では無視される |
| 0 (board) | 0x0037 | black_th: 非黒判定の閾値(成分の上位5bit と比較, 0..31)。既定0。**上げると暗い絵の中身が範囲から外れて送られなくなる** |
| 0 (board) | 0x005E | clamp_sel (TVP reg 10h[2:0]): bit2=Blue bit1=Green bit0=Red。0=ボトム 1=ミッド |
| 0 (board) | 0x005F | coarse_gain_gb (TVP reg 1Bh): **[7:4]=Green [3:0]=Blue**。Gain = 0.5 + N/10 |
| 0 (board) | 0x0065 | coarse_off_g (TVP reg 1Fh[5:0]): 粗アナログオフセット Green。10h=+64コード |
| 0 (board) | 0x0067 | coarse_gain_r (TVP reg 1Ch): **[7:4]=Reserved [3:0]=Red**。1Bhとビット割りが違う |
| 0 (board) | 0x0068 | coarse_off_r (TVP reg 20h[5:0]): 粗アナログオフセット Red |
| 0 (board) | 0x0069 | in_mux1 (TVP reg 19h): [7:6]=SOG [5:4]=R [3:2]=G [1:0]=B、00=_1/01=_2/10=_3 |

**0x0035 の対モード(bit4)は、フィールドごとに VSYNC が来るインターレース
(480i など)で2フィールドを1単位として間引く。** フィールドを1枚ずつ数えると、
1/2 で片方の極性のフィールドしか届かず、もう片方は古いまま残って織り込みが崩れる。
対モードでは連続する2フィールドを送ってから N 単位(=2N フィールド)飛ばす。
プログレッシブと、1回の VSYNC に2フィールド入る信号(X68000 24kHz など)では
無視される(もともと1単位がフレーム全体)。対の始まりの極性は揃えない
(受信側は半ライン位置で織り込むので順序に依存しない)。
**古いゲートウェアは bit3:0 しか保存せず、GET でも bit4 を返さない**ので、
受信側は読み戻しで対モードの有無を判別できる

**0x005E と 0x005F は必ずセットで動かす。** ミッドレベルクランプにするとブランキングが
コード512に座るので、白側(+100 IRE)に使えるヘッドルームが半分になる。既定の粗ゲイン
1.2倍のままではコンポジット(1Vpp=140 IRE)が飽和する(データシート 1Bh は
「Vpp × Gain < 1Vpp」を要求する)。数値の内訳は `composite-video-plan.md` §2。

**0x005F と 0x0067 は同じ「1.2倍」でも値が違う**(1Bh=0x77 / 1Ch=0x07)。
1Bh は Blue と Green の2チャネルぶんを1バイトに詰めているため。

**0x0069 は入力方式の切り替えに必須。** 以前はビルド時定数だったので、SOG の入力ピンが
違う機種(MSXのC-SYNCは SOGIN_2)に切り替えるにはビットストリームの焼き直しが要った。
なお **HSYNC_A/_B・VSYNC_A/_B の選択は 19h ではなく 1Ah bit0/bit2**(key 0x005D)。

- 0x0010〜0x002C・0x0030〜0x0036・0x0040〜0x0045 は画枠パラメータと診断用の
  読み出しに割り当て済み。**新しい設定キーは 0x0050 以降から取る**
  (0x0023〜0x0026 は診断キーと衝突する)
- **0x0013〜0x0016 は空いていない。** インターレース判定が「設定」から「測定」へ
  移ったのでゲートウェアは読まなくなったが、`CFG_KEY_INTERLACE` などの名前が
  host/client に残っているので再利用してはいけない。
  現時点で真に空いているのは 0x002E〜0x002F / 0x003A〜0x003F / 0x004E〜0x004F /
  0x006B 以降(0x0046〜0x004D は個体設定で使用)

キーの割り当ては `host/python/retrocastx/protocol.py` の `CFG_KEY_*` を正とし、
ゲートウェア側は `gateware/retrocastx_stream.py` の `reply_cases` と対応させる。

- ArgusX宛のCONFIGは、ゲートウェアがI2Cバス(TVP7002と共有、J11コネクタ)経由で
  ArgusXへ中継する。ArgusXのI2Cアドレス・レジスタマップはArgusX側で確定後に反映
- 認証なし(同一LAN前提)。SETは全て冪等な値設定のみとする
- **ブロードキャスト可**(SUBSCRIBEと同様)。PCとボードのサブネットが食い違う構成
  (直結・DHCPなし等)ではユニキャストがOSのルーティングで送れないため、
  アプリはCONFIGもブロードキャストで送ってよい。ただし同一LANの全ボードに
  適用されるため、複数ボード環境ではDHCP導入後にユニキャストで送ること
- ブロードキャストで送る場合、**アプリは応答の flags bit0(REPLY)を必ず検査する**。
  ブロードキャストは自分自身の送信パケットにもループバックするため、REPLYを見ないと
  自分の要求を応答と誤認し、SETが常に成功・GETが常に送った値に見える(実際に踏んだ)

### シリアルLED(0x0090〜0x0095、表は 0x0400〜0x05FF)

| target | key | 意味 |
|---|---|---|
| 0 (board) | 0x0090 | 小亀基板のLEDの個数(1〜8)。既定 4 |
| 0 (board) | 0x0091 | 再生するキーフレーム数(0=消灯)。既定 6(内蔵のレインボー) |
| 0 (board) | 0x0092 | 再生するバンク(0/1)。既定 0。**書き換えると先頭から再生し直す** |
| 0 (board) | 0x0093 | 小亀基板のLEDの明るさ(0〜255)。既定 64 |
| 0 (board) | 0x0094 | 状態LED(メイン基板 D1)の明るさ(0〜255)。既定 32 |
| 0 (board) | 0x0095 | 状態LEDの状態。**読み取り専用**。0=赤(10秒間 Viewer から何も来ていない) / 1=橙(SUBSCRIBE(発見のみ)か CONFIG が来ている) / 2=青(本購読中=映像・音声を送信中) |
| 0 (board) | 0x0400〜0x04FF | キーフレーム表 バンク0(256語)。GET で読み返せる |
| 0 (board) | 0x0500〜0x05FF | キーフレーム表 バンク1(256語) |

- 表の形式: フレーム k の先頭語 = k × (1 + LED数)。先頭がヘッダ
  (`[15:0]`=保持[ms] / `[31:16]`=フェード速度)、続いて LED ごとの色 `0x00RRGGBB`。
  保持のあと次のフレームへ線形にフェードし、最後のフレームの次は先頭に戻る
- フェード速度は「1ms ごとに16bitの位相へ足す量」= 65536 / フェード時間[ms]。
  **割り算はアプリ側でする**(FPGAで割らないため)。0 はフェードせず切り替え
- 書き換えは**再生していない方のバンク**へ表を書き、全語の応答を確かめてから
  0x0090/0x0091/0x0092 を書く(書きかけの表が光らない)
- **ボードの CONFIG 応答は1つしか溜まらない**ので、表は1語ずつ応答を待って送る。
  まとめて投げると応答が上書きされ、届いたかどうか確かめられない
- 設定はボードに残らない(電源で既定に戻る)。アプリが繋ぐたびに送り直す
  (下の 0x0097 だけは EEPROM に焼ける)

### 小亀のLEDの切断中の動作(0x0097、gw-v1.4.0 以降)

| target | key | 意味 |
|---|---|---|
| 0 (board) | 0x0097 | Viewer が居ないあいだ(映像を送っていないあいだ)の小亀基板のLED。0=そのまま光らせる(既定) / 1=呼吸 / 2=消灯 |

- **ボードが自分で切り替える。** 居ないあいだは Viewer が指示できないため。
  状態LEDが青(本購読中)でないあいだ効く
- 呼吸は**明るさだけ**を約6秒周期で上下させる(山は 0x0093 の明るさの1/4、谷は消灯)。
  表の再生は止めないので、固定色ならその色、レインボーなら色を回しながら明滅する
- 値は個体設定と同じ扱い: SET は即座に効き、**0x004C で EEPROM(設定ページの 0x09)に
  焼ける**。焼けば電源投入直後から効く。**0x004C に 2 を書くとこの欄だけを焼き**、
  名前・IP・net_mode は EEPROM にある値のまま書き直す(0x0046〜0x004B の未保存の
  試しを巻き込まない。ボードは EEPROM の中身の写しを持っている)。1 はすべて焼く
- ANNOUNCE の caps bit2(CAP_LED_IDLE)で対応を判別する。古いゲートウェアには書かない

| target | key | 意味 |
|---|---|---|
| 0 (board) | 0x0096 | 小亀基板のアナログスイッチ(FFC 15 = SO-DIMM 148 / K4)。0=コンポジット/コンポーネント(既定) / 1=S端子 |

- 0 のとき FFC 9 = CVBS・FFC 7 = Pr、1 のとき FFC 9 = S端子Y・FFC 7 = S端子C

## INFO / ANNOUNCE パケット(type=3)

ボードの自己紹介。**発見(Discovery)と生存確認**に使う。共通ヘッダに続き 32 bytes:

共通ヘッダの flags は、映像の送り先の状態を **この ANNOUNCE の宛先から見て** 返す:

| bit | 名前 | 説明 |
|---|---|---|
| 0 | OWNER_INFO | bit1/bit2 が有効。gw-v1.3.0 より前のゲートウェアは flags=0 |
| 1 | STREAMING | 購読が生きている(映像をどこかへ送っている) |
| 2 | YOURS | その送り先が、この ANNOUNCE の宛先(IP とポート)と同じ |

Viewer はこれで「他の Viewer に奪われた(STREAMING=1, YOURS=0)」と
「ボードが再起動した・購読が切れた(STREAMING=0)」を見分ける。映像が止まる
という症状だけでは両者を区別できない。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | 6B | mac | ボードのMACアドレス |
| 14 | 4B | ip | ボードが自認するIPv4(参考値。**受信側はUDP送信元アドレスを正とする**) |
| 18 | u16 | udp_port | データ/制御ポート |
| 20 | u16 | fw_version | ファームウェアバージョン |
| 22 | u16 | caps | 能力ビット(bit0=TVP7002, bit1=アナログ音声, bit2=S/PDIF, bit3=ArgusX接続) |
| 24 | 16B | name | ボード名(UTF-8, NUL詰め)。EEPROMの設定ページ由来。未設定なら `retrocastx-i5` |

## SUBSCRIBE パケット(type=4)

アプリ→ボード。共通ヘッダに続き 8 bytes。**ブロードキャスト可**。

| offset | size | field | 説明 |
|---|---|---|---|
| 8 | 6B | mac | 宛先ボードのMAC。全FF(`ff:ff:ff:ff:ff:ff`)=ワイルドカード(全ボード) |
| 14 | 2B | reserved | 0 |

- ボードは **mac が自分のMACと一致、またはワイルドカード** のときのみ反応する。
  一致しなければ完全に無視(応答もストリーム切替もしない)
- flags bit0 = ANNOUNCE_ONLY: 1なら発見のみ(ボードはANNOUNCEを送信元へユニキャスト返信)
- flags bit0 = 0 なら、ボードは以後の映像ストリームの送り先を**このパケットの送信元**に切り替え、
  ANNOUNCEを返す。購読は最後のSUBSCRIBEから10秒で失効(アプリは定期再送する)
- flags bit1 = RENEW: 延長専用。送信元(IP とポート)が**いまの送り先と同じときだけ**
  失効までの時間を延ばし、違えば送り先を変えない(ANNOUNCE は返す)。
  gw-v1.3.0 から。それより前のゲートウェアは bit1 を見ないので、通常の SUBSCRIBE として効く
- **送り先は後勝ち。** 奪うのは通常の SUBSCRIBE で、Viewer は起動時・ボードを選んだとき・
  「接続」を押したときだけ出す。定期の延長は RENEW なので、奪われた Viewer が
  延長しても奪い返さない(以前は2秒ごとの再送が毎回奪い、2台の Viewer が交互に
  奪い合った)。奪われた Viewer は返ってきた ANNOUNCE の flags でそれを知って止まる
- **複数ボード運用**: ワイルドカードでの本購読(ANNOUNCE_ONLY=0)は全ボードが同時に
  ストリームを向けてくるため単一ボードLAN専用。複数ボード環境では
  ①ワイルドカード+ANNOUNCE_ONLY で発見 → ②ANNOUNCE で各ボードのMACを取得 →
  ③目的ボードのMACを指名して本購読、とする(ブロードキャスト送信のままでよい)

## アドレッシングと発見の設計

- **MACアドレス**: 基板のEUI-48 EEPROM(24AA025E48、ポートごとに1個)から
  起動時に読み出したグローバル一意アドレスを使用。EEPROM未実装/読出し失敗時は
  ローカル管理アドレス `02:52:43:58:xx:xx`("RCX"、既定 `02:52:43:58:00:01`)に
  フォールバック
- **個体設定の保存先**: MACと同じ EUI-48 EEPROM の空き領域(0x00..0x1F)。
  0x00-01 magic 'RX' / 0x02 ver / 0x03 flags / 0x04-07 静的IP / 0x08 チェックサム /
  0x09 小亀のLEDの切断中の動作 / 0x10-1F 名前。**書込みは8バイトページ単位で、ヘッダ(magic のあるページ0)を最後**に
  焼く。途中で電源が落ちたページは magic が古いまま = 「未設定」として捨てられる
- **発見はアプリ起点**: アプリが `255.255.255.255:34600` へ SUBSCRIBE(ANNOUNCE_ONLY) を
  ブロードキャスト → ボードがユニキャストで ANNOUNCE 返信。
  ボード側受信はブロードキャスト対応(LiteEth `with_broadcast=True`)なので、
  **ボードとPCのサブネット設定が食い違っていても同一L2セグメントなら発見できる**
- **IPアドレス**: 既定は **MAC由来のリンクローカル**(RFC 3927、`169.254.<mac[4]>.<mac[5]>`、
  第3オクテットは 1..254 に丸める)。基板ごとに違う値になるので、複数台を同じLANに
  繋いでも衝突しない。**固定の 192.168.10.50 は繋ぐ相手を選んだ**ため廃止
- **静的IP**: CONFIG 0x0046/0x0047 で設定し、0x004C で EEPROM に焼ける。
  ルータを跨ぐ構成(ブロードキャストが届かない)向けの逃げ道。
  **既定はオフ。** 自前のツールはどれも固定IPを必要としない(発見はブロードキャスト、
  映像の送り先は SUBSCRIBE の送信元)ので、通常は設定する理由が無い
- **設定を間違えても行方不明にはならない**: 受信は宛先IPを見ずに通し
  (LiteEth `with_broadcast=True`)、応答は受信パケットから学習したMACへ返すので、
  **サブネットが食い違うPCに直結してもブロードキャストで発見でき、その場で戻せる**
  (実測: ホストが 192.168.11.0/24 のみ、ボードが 169.254.132.41 の状態で
  `discover` が発見)
- **DHCP** は LiteEth 同梱のハードウェアDHCPクライアント(`liteeth/core/dhcp.py`)で
  導入できる。**入れるならリンクローカルで先に上げ、リースが取れたら乗り換える**:
  OSのAPIPAが嫌われるのは「先にDHCPを待って、諦めてから」落ちるからで、
  自前実装なら逆順にできる(RFC 3927 も並行動作を認めている)。
  アプリ→ボードは全てブロードキャスト可、ボード→アプリは宛先を直接解決する
  (ゲートウェイ概念なし=全てオンリンク扱い)ため、DHCPサーバの無い直結構成
  (PC側も169.254.x.x自己割当)でもサブネット不一致のまま全通信が成立する。
  ただし**ARPで引くだけでは足りない**: Windows は別サブネットの送信元から来た
  ARP要求に応答しない(strong host model)。そのためボードは**受信パケットから
  相手のMACを学習**して返す(`gateware/retrocastx_net.py`、design-notes 参照)
- 映像の送り先はSUBSCRIBE送信元に動的に決まるため、アプリ側のIP設定は不要

## 帯域の目安

| モード | アクティブレート | RGB888 | RGB555 |
|---|---|---|---|
| 768×512@55.46(X68000 31kHz) | ~24 Mpx/s | ~580 Mbps | ~390 Mbps |
| 640×400@56.4(PC-98 24kHz) | ~14 Mpx/s | ~350 Mbps | ~230 Mbps |
| 512×512@55.46(X68000 15kHz) | ~8 Mpx/s | ~190 Mbps | ~130 Mbps |

ヘッダオーバーヘッドは 20B/ライン + UDP/IP/Ether 42B ≒ ライン当たり 62B(2304B に対し 2.7%)。

## 受信側の再構成方針

1. MODE を受けてフレームバッファ(hactive×vactive)を確保
2. LINE を `frame`/`line`/`offset_px` に従って書き込み
3. VSYNC 相当は「`frame` が進んだこと」で検出(将来: FRAME_END フラグの追加を検討)
4. 表示は 2 通り:
   - **フレーム同期モード**: フレーム完成を待って表示(実装が簡単、遅延 ≦1フレーム)
   - **レースザビームモード**: 受信したラインから逐次テクスチャ更新(最小遅延、VRR 前提)
5. パレット吸着(オプション): 機種プロファイル(例: X68000 = RGB 5bit)に基づき
   受信 8bit 値を最近傍のネイティブパレット値にスナップ
